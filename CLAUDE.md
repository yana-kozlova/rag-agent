# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
pnpm dev              # Start Next.js dev server (http://localhost:3000)
pnpm build            # Production build
pnpm lint             # ESLint
pnpm test             # Run all tests with Vitest
pnpm db:generate      # Generate Drizzle migrations
pnpm db:migrate       # Run migrations (tsx lib/db/migrate.ts)
pnpm db:push          # Push schema directly to DB
pnpm db:studio        # Open Drizzle Studio

pnpm kb:backfill      # Extract entities from notes saved before the graph existed
pnpm kb:compact       # Strip the old prose restatements out of saved notes
pnpm timeline:backfill # Read dates out of notes saved before the timeline existed
pnpm wellbeing:canonicalize # Re-match old symptom labels against the user's vocabulary
pnpm images:prune     # Forget image URLs whose blob object is gone
```

All five maintenance scripts take `--dry`.

Tests live in `test/` and match `test/**/*.test.{ts,tsx}`. Vitest resolves the `@/` alias via `vite.config.ts`.

## Architecture

**Next.js 14 App Router** personal assistant with RAG (Retrieval-Augmented Generation), Google Calendar integration, and a chat UI.

### Core Data Flow

1. **Chat** (`app/api/chat/route.ts`): Streams AI responses via Vercel AI SDK (`streamText`). Uses OpenAI models (configurable via `AI_CHAT_MODEL` env var, defaults to `gpt-4o-mini`). The system prompt is in `app/prompts/system.ts` and gets tool descriptions injected at runtime.

2. **RAG Pipeline** (`lib/ai/embedding.ts`): Text is split into chunks (adaptive by content type: code, lists, tables, paragraphs), embedded via OpenAI (`text-embedding-3-small`), and stored in `embeddings` table with pgvector HNSW index. Retrieval runs two retrievers over the same chunks — pgvector cosine and Postgres full text — and fuses their rankings (`lib/ai/retrieval.ts`), with configurable `RAG_TOP_K` and `RAG_EF_SEARCH`.

**Fusion has to survive all the way to the model.** Every ranking decision retrieval makes — the two retrievers, reciprocal rank fusion, the recency tiebreak, the several phrasings `expandQuery` produces — is expressed as one number, `score`, on each row. `getInformation` used to sort its results by `similarity` and throw that number away, so the final order the model saw was pure cosine and the lexical half could only ever change which chunks were *available* for cosine to sort. It also filtered on `similarity > MIN_SIMILARITY`, which deletes a lexical-only hit by construction: a chunk holding an invoice number, a surname or a version scores low against the question because the rest of it is about something else — that is precisely why the embedding did not rank it and precisely why full-text search exists. So `similarity` stays what its name says and rides alongside `score`; `aggregateResults` keys on the chunk id and *adds* the scores each phrasing awarded, because agreement between phrasings is evidence and can only count if it accumulates; and `isRelevant` admits a lexical hit whatever its cosine. Results are then spread across sources (`MAX_PER_SOURCE`), since a long document is many chunks about one subject and ranking alone hands it every slot while the note that answers the question sits sixth.

**A lexical query must not be a query for everything.** `ts_rank_cd` has no IDF — a term in every chunk is not discounted — and the terms are OR'd, so one function word puts the whole base in the candidate list ranked by how often each chunk happens to say "за", and the `LIMIT` then cuts off the chunk that actually matched. The prefix wildcard made it worse: `за:*` also matches "завтра", "заняття", "записати". `STOPWORDS` in `lib/ai/retrieval.ts` is therefore shared with `heuristicVariations` so that "not a content word" means one thing here, and `:*` is only attached where truncation actually happened — a token at or under `MIN_PREFIX_LENGTH` loses nothing to truncation, so a wildcard on it cannot reach a single inflected form ("рука:*" finds "рукав", never "руки") and adds only noise. A question with no content words left returns null, which skips the lexical retriever: there is no exact match to look for in a sentence made of grammar, and a list ranked by stopword frequency entering fusion at rank 1 is worse than no list.

**`hnsw.ef_search` is the recall knob, and pgvector's default is narrower than what this asks for.** The index cannot return more rows than it looked at, so requesting `topK × 4` candidates at the default 40 draws the answer from a list barely wider than the answer. It is set per-query via `set_config(..., is_local => true)` inside a transaction, so a pooled connection is left as it was found, with the plain query standing behind it — a database whose pgvector predates the setting must lose the widening, not the whole vector half.

**Embed first, write second.** `createResource` and `updateResource` generate embeddings *before* touching any row, and swap text and vectors in one transaction. The old order wrote the row, deleted the old vectors and then called OpenAI; a failure at that last step left a note that reads correctly on its page and appears in no search, permanently, with nothing retrying it. Since folding a fact into an existing dossier is now the ordinary way a note is saved, that window was not rare — and worse, `addResource` reads a failed update as "save it as a new note instead", so a merge that got that far wrote the merged content into the dossier *and* created a second note saying the same thing. Generating first is what makes that fallback correct.

3. **Resources** (`lib/actions/resources.ts`, `lib/db/schema/resources.ts`): User-uploaded content (documents, notes, images) stored with metadata. Each resource generates embedding chunks. Supports PDF, DOCX and EPUB extraction (`unpdf`, `mammoth`, `lib/utils/epub.ts`).

**`metadata.type` has one list, and the Knowledge Base filter is counted, not written.** The type enum lived in four hand-maintained copies — the zod schema, the extractor, the `/resources` filter dropdown and its edit form — and they drifted apart: the filter offered types nothing carried while omitting `image`, `event`, `preference` and `need`, so notes the extractor had been classifying for months were unreachable from the page whose job is to reach them, and re-saving a `preference` through the editor silently retyped it to `note`. `lib/utils/resource-types.ts` is now the only list (in `lib/utils` so a client component can import it without dragging drizzle into the browser — same reason as `lib/utils/uploadable.ts`); `EXTRACTABLE_RESOURCE_TYPES` is it minus `image`, which the vision path assigns from the fact that bytes arrived and no model may infer from prose. The filter's options come from `collectFacets` (`lib/utils/resource-facets.ts`) counting the user's own rows, shared by the page's first paint and `/api/resources/tags` so the two cannot disagree. An unrecognised type is kept and sorted last rather than dropped — `metadata` is `passthrough()`, and hiding a row is the original bug in a new costume — and an absent type counts as `note`, which is why the API filters on `coalesce(metadata->>'type', 'note')`.

**Images are stored as text.** A photo or screenshot is read once at the door by a vision model (`lib/ai/vision.ts`, `AI_VISION_MODEL`, defaults to the chat model) which names what it shows and transcribes any text on it verbatim; that description becomes the resource's `content`, so chunking, embedding, extraction and hybrid search all work unchanged and never learn about a second modality. The bytes go to Vercel Blob (`lib/storage/images.ts`, `BLOB_READ_WRITE_TOKEN`) and the URL is kept in `metadata.imageUrl`. Both halves degrade independently and on purpose: a failed description aborts the upload (an unsearchable image is invisible to the assistant), while a failed store only logs and the resource is saved without a URL. `lib/actions/save-image.ts` owns that ordering so no surface re-decides it. Note that Vercel Blob has no private tier — every object is served publicly and the unguessable URL is the only protection, so nothing harmful-if-leaked belongs here. A store that is deleted and recreated gets a new id, which orphans every URL already saved against the old one: the row still claims a picture, and the Knowledge Base card renders an empty box where the description preview would have been. `pnpm images:prune [--dry]` drops `imageUrl`/`imagePathname` from those rows and nothing else — the description is still true and still searchable, and a resource without a URL is the state an upload with no `BLOB_READ_WRITE_TOKEN` already produces. Only an explicit 404 or 410 counts as gone; a timeout or a 5xx means "could not tell", and erasing a live URL on that evidence is the one mistake here nothing can undo. Client-side pickers validate against `lib/utils/uploadable.ts`, which is dependency-free precisely so a client component never pulls `unpdf`/`mammoth`/the AI SDK into the browser bundle.

**An EPUB is read in spine order.** An EPUB is a ZIP of XHTML read in the order the package document's *spine* gives, not filename order — concatenating the files alphabetically scrambles the book and makes retrieved passages read as if they came from the wrong chapter. Extraction lives in `lib/utils/epub.ts` (no XML parser: the two files that need reading have a flat shape and the rest is being reduced to text anyway); DRM-protected books are detected via `META-INF/encryption.xml` and refused, because their XHTML unzips fine and decodes to noise.

**A note is a dossier, not a transcript of one message.** `addResource` used to insert unconditionally, so one message about Andriy produced two notes 900 ms apart and the graph split the owner's identity three ways behind them. It now routes: `findDossier` (`lib/actions/note-routing.ts`) looks for an existing note *about the same subject*, and `updateResource` folds the new fact into it. The routing is deterministic on purpose — a note qualifies only when the incoming content has exactly one graph-worthy entity, is under `MAX_ROUTABLE_LENGTH`, and the target note has that entity as its **sole** subject. The alternative, asking an embedding whether two texts are "the same", needs a threshold thin enough to separate "Андрій is my husband" from "Андрій was born in 1985" — two different facts about one person, sitting very close together. Routing by subject removes that razor; a big import therefore always becomes a new note rather than being smeared over everyone it mentions.

**A note is stored once, not five times.** `formatStructuredContent` (`lib/ai/information-extraction.ts`) writes the summary and the key points — nothing else. It used to append the facts, the entities and the needs as prose too, so one request for a pediatrician's certificate was stored as a paragraph, the same thing as bullets, again as subject-predicate-object, again as "name - type (relationship)", and once more as a need: 190 characters of information kept as 743. All three are already in `metadata` in the machine-readable form the graph and the merge check read, and prose copies of them were never the source of anything. The second-order costs were the expensive part — retrieval scored five near-identical chunks where one claim existed, and the inflated length was measured against `MAX_ROUTABLE_LENGTH`, so a one-line fact about Артем cleared 600 characters, was declined as an import, and became the second note about a person who already had one. That is the exact duplication the routing exists to prevent, caused by the routing's own preprocessing; `addResource` now measures what the user typed. `keyPoints` stays in the text because the embedding is built from it and that is where the dates and names are. `pnpm kb:compact [--dry]` takes the old restatements back out of notes already saved and re-embeds them, removing a line only when regenerating it from that note's own metadata reproduces it character for character — so text since merged, rewritten or hand-edited is left alone.

**A rewrite is never trusted to keep what it was given.** `mergeNoteContent` (`lib/ai/note-merge.ts`) asks the model for a merged note, then checks every fact from the old note's `metadata.facts` still has its subject and object present — predicates are allowed to be rephrased, anchors are not allowed to vanish. A rewrite that drops one, or that collapses below `MIN_LENGTH_RATIO` of the original, is discarded and the new material is appended instead. Worse prose, zero silent loss. The anchors are matched word by word, minus stopwords and minus a long token's last character. Matching each anchor as one string only ever worked because the note being checked *contained the fact list verbatim* — once the restatements above were gone the same fact had to be recognised in the summary carrying it, where it reads "a medical certificate from a pediatrician for her child, Artem" and no contiguous run matches. A check that strict would reject every rewrite and silently turn merging back into appending, which is how a note starts repeating itself again; the trailing character goes because the merge prompt answers in the note's language and Ukrainian inflects "Андрій" to "Андрія", where neither string contains the other.

**A note is written in the language the user typed it in.** Nothing ever said "write in English", but the extraction prompt's only worked example took a Ukrainian message and returned English facts, entities and a summary — a demonstrated translation is a stronger instruction than any sentence, so a Ukrainian base was stored in English. The cost is not aesthetic: `addResource` keeps only the extractor's output as the note's `content`, so the words the user typed survive nowhere, the lexical retriever holds English tokens while the question arrives in Ukrainian, and `entities[].name` becomes whatever the model transliterated this time. Identity is `(user_id, normalized_name, type)` and `normalizeName` only lowercases, so "андрій" and "andriy" are two rows — and `findDossier` matches that same key exactly, so a spelling that drifted between two saves fails to find the dossier and writes a second note about a person who already has one. That is the duplication note routing exists to prevent, caused upstream of it. The rule is therefore the source language, not a setting: forcing a chosen language would translate a pasted English article out of its own vocabulary, and applying it to names would make the graph split *toggleable*, which is worse than a split that is at least deterministic. Four fields stay English whatever the message says — `contentType`, each entity's `type`, each need's `priority` and every tag — because they are matched against code: `GRAPH_TYPES` is an English set, and an entity typed "особа" is silently never made a node. Two worked examples now carry the rule in both directions, since one Ukrainian example alone would just reverse the bias.

A fact about the account holder is extracted with a *placeholder* subject — the word for "user" in the message's language, never their name — and those words are in `note-merge`'s `STOPWORDS`. The subject of such a fact is a word the note itself has no reason to contain: it names the person or speaks in the first person. Anchoring on it passed only while notes were English and the summary happened to open "User requests…"; in Ukrainian every fact about the user would read as dropped, rejecting every rewrite and turning merging back into appending with nothing in the log. The object is what carries the claim, and it is still checked.

**Entity identity is resolved by the user, made permanent by aliases.** `lib/actions/entity-identity.ts` folds names (Cyrillic → Latin, `y`/`j`/`i` collapsed, repeats squashed) so "Андрій"/"Andriy" and "Yana"/"Yana Kozlova" can be *suggested* as one person — deliberately over-eager, because a declined suggestion costs a click and a missed one splits the graph forever. Nothing merges automatically: `findMergeCandidates` proposes, the user confirms in `app/entities`, `mergeEntities` repoints mentions and drops the loser. Merging alone would not survive, since identity is `(user_id, normalized_name, type)` and the next note would recreate the node — so a merge writes an `entity_aliases` row, and `syncEntitiesForResource` consults it before creating anything. Two exceptions: the account holder is collapsed automatically (`resolveSelfName`) because the signed-in name is known and it is not a judgement call, and a shared surname is never offered as a match.

**Renaming a node and merging two are the same operation, and both are alias writes.** The suggestion rules are narrow by construction, so the pairs they cannot propose — a bare surname against a full name ("Коваленко" is not a prefix of "Андрій Коваленко"), a diminutive, an abbreviation, a name filed under two types — need a hand, and the correction is one question: *this is actually…*. `EntityIdentity` on `/entities/[id]` asks it once; a name that already belongs to a node becomes `mergeEntities`, and a name that belongs to nothing becomes `renameEntity` (`lib/actions/entity-rename.ts`). Editing `entities.name` alone would be pointless — the column is "as last written by the model" and `syncEntitiesForResource` rewrites it on the next mention — so a rename writes two `entity_aliases` rows, the old spelling so notes still using it land here instead of recreating the node, and the new one so nothing overwrites the name the user just chose. That is also why the alias path in `syncEntitiesForResource` still fills in `relationship`: skipping the upsert must cost the spelling, not everything later notes learn. `planRename` separates a *respell* (same normalized name, so it cannot collide) from a *rename* (a new identity, so an occupied one is reported back as the merge that was meant). Merging across types is allowed here though never suggested — nothing in the transaction depends on types matching, the winner's survives, the alias keeps the loser's, and the model files one project as `project` and `organization` often enough that this is the ordinary manual case. Manual merge stays as irreversible as the suggested kind, which is why the confirmation spells out what moves and which name disappears, and why direction is switchable rather than decided by `pickWinner`.

**Deleting a node is a standing rule, not a row — and it is the one entity action that can be undone.** Rename and merge both assume the node names something; neither answers the third way the graph goes wrong, which is a node made of what was never a subject — a greeting read as a person, a stray noun read as a place, the liberality of extraction showing through. A bare delete would not survive: `entities` is the projection of every note's `metadata.entities`, so the next mention upserts it straight back, and it returns with a mention count of one while twenty notes still talk about it, which reads as data loss rather than as a delete that failed. So `deleteEntity` (`lib/actions/entity-delete.ts`) writes `entity_exclusions`, the mirror of `entity_aliases` — an alias says a spelling means *that* node, an exclusion says it means nothing, and `syncEntitiesForResource` consults both before the upsert. Keyed on the same triple as `entities.identity`, so burying the project called Sequoia says nothing about the place; the node's own aliases are buried alongside it, or a node that had absorbed three spellings rebuilds itself under one of the other two. Nothing the user wrote is touched — the notes keep their words and their `metadata.entities`, retrieval still finds them, `timeline_events.entity_id` sets null rather than cascading — and that is precisely what lets `restoreEntity` rebuild the node rather than only lift the tombstone: the evidence is still there, so the sync is replayed over the notes that still name it, capped by `MAX_REBUILD` because a two-letter name matches a lot of prose. A merge or a rename calls `clearExclusions` on the spellings it claims, since the later decision wins and a tombstone standing over a live node would list a name as hidden while its page is open. The buried names are shown on `/entities` rather than nowhere: a delete that quietly filters every future save is indistinguishable from a bug unless it can be read back and lifted.

**A relationship is to the user, and the user gets the last word on it.** Merge, rename and delete all repair a node's *identity*. The fourth thing that goes wrong leaves the identity correct and the one editorial line wrong: `entities.relationship` means "how this node relates to **the user**", and extraction fills it with whatever relation the sentence happened to state. "Артем — похресник моєї куми" is a true sentence about the godmother, and it is stored as *the user's* godson — so a son is labelled a godson on his own page, in the entity list, on the people widget and in the note view, in each case printed beside the name as fact rather than as evidence. The prompt now says the field is to the user and nobody else, and that a third-party relation is either written out in full ("godson of the user's kuma") or left null; the schema's `describe` says it too, since that is what the model actually reads. But a prompt is a tendency, so `setRelationship` (`lib/actions/entity-relationship.ts`) is the correction — and it has to be a decision rather than an edit for the same reason a rename does, because `syncEntitiesForResource` rewrites this column from every note that mentions the node and a plain edit would revert at the next mention with nobody watching. `entities.relationship_source` (`model` | `user`) is what the sync consults, in both branches: the alias path updates only where the source is still `model`, and the upsert's `coalesce` sits inside a `case` on it. One flag on the row rather than a table like `entity_aliases`, because unlike a name this value rides on a row the sync updates in place and never recreates. Blank is an answer and not an absence — "they are nothing in particular to me" is exactly the correction a wrongly-lifted relation needs, so the source is what a merge keys on and `pickRelationship` gives a hand-set value the win from either side (which of two duplicates survives is decided by mention count, something the user never sees and never chose). `resetRelationship` hands the field back to extraction and leaves the current wording standing, since the notes are untouched and the next mention fills it in again; that undo is possible for the same reason `restoreEntity`'s is. The one thing it does not survive is a delete, which drops the row — a restored node comes back with the model's reading.

**Books are the reason embedding is batched.** A book chunks into the high hundreds, past OpenAI's per-request ceiling of 2048 inputs / 300k tokens, so `generateEmbeddings` splits into sequential batches — one request per book would fail on exactly the uploads this was built for. For the same reason `extractStructuredInformation` reads only the first 60k characters: a whole book exceeds any chat model's context, and an over-long prompt fails both attempts and leaves the book with no tags, facts or entities at all.

4. **Timeline** (`lib/db/schema/timeline.ts`, `lib/timeline/`, `lib/actions/timeline.ts`, `app/timeline/`): the dates a life is measured by — births, moves, weddings, first days, trips, diagnoses — on one ordered axis.

**Prose cannot be sorted by when.** The base could already hold "Артем народився 12 березня 2019" as an embedded, findable note. What it could not do is put it in order: nothing answered "що було у 2022?", nothing knew a birthday was three days out, and a note about a move sat in the same undifferentiated pile as a preference about oat milk. So a date is stored twice, on the `wellbeing_entries` precedent — the note keeps its wording and stays searchable, `timeline_events` keeps the day. `metadata.dates` is the note's own record of what extraction found; the table is the projection of every note's into one series, exactly as `entities` is the projection of every note's `metadata.entities` into one graph. It is written from the same two places, on the same terms: `createResource`/`updateResource` sync it, `replace` drops only that note's rows, and a failure is non-fatal because a note without its dates is still a saved note.

**How much of a date is known, and whether it comes round, are two different columns.** Conflating them is what makes a naive events table wrong within a week. `precision` (`day` | `month` | `year` | `day-month`) says which components of `occurredOn` are real — "ми переїхали у 2022" is a year, and a column that keeps only a `date` turns it into 1 January and then prints it back as if someone had said so. `recurrence` (`none` | `annual`) is orthogonal: a wedding on a known day recurs, a known-to-the-day hospital visit does not. `day-month` is the case that forces the split — "у Андрія день народження 14 березня" gives a real day and month and no year, so its stored year is `PLACEHOLDER_YEAR` (2000, a leap year, because `--02-29` is a real birthday and has to survive being stored), is never printed, and keeps such a date off the historical axis entirely: it has no origin point to place, only occurrences ahead of it. That is also why "виповнюється N" is computed only when the original year is real — an age is a claim about a year nobody recorded. Dates are formatted in `timeZone: 'UTC'`, because a calendar date parsed as an instant is UTC midnight and rendering it west of Greenwich prints the day before.

**The hard part is refusing most dates.** `DATE_EXTRACTION_RULES` (`lib/ai/information-extraction.ts`) is one constant shared by the full extraction and by the dates-only pass the backfill runs, so the two cannot drift. It admits what a person would still name years later and rejects the note's own created-at, times of day, routines, vague futures, and ordinary appointments — those live in the calendar, which already holds them. A knowledge base whose timeline fills with "the meeting is on Tuesday" has a timeline nobody opens twice. The prompt is given the user's own today (`todayFor`), not the server's: at 01:00 in Kyiv the server is still on yesterday, and a relative date filed a day early is never noticed and never corrected. `MAX_DATES_PER_NOTE` caps what one import can contribute — a document about a war produces forty dates, none of them the user's.

`rememberDate` exists beside all that because extraction cannot produce a yearless date from prose reliably: asked for "день народження 14 березня" it guesses a year, and the birthday quietly becomes a one-off in 2026. Stating it outright is also the only way to *correct* a date, since a second note about the same day is a second note. Deleting is an API route, not a tool, on the wellbeing precedent. Identity is `(user_id, occurred_on, kind, subject_key, lower(btrim(title)))` — deliberately conservative: it will not catch "Артем народився" against "народження Артема", and that is the safer direction to fail, because a visible duplicate can be deleted and a silently swallowed second event on the same day cannot be recovered. `resource_id` cascades (the note is the evidence) while `entity_id` sets null (losing a node is no reason to forget when their child was born), and a date the user typed has neither, so nothing that happens in the knowledge base can touch it.

Upcoming dates ride into the morning briefing through `dateLines`, built by the application exactly as `scheduleLines` is — a model told a birthday is in three days will eventually say two. An empty calendar no longer means an empty briefing: a birthday tomorrow is the whole reason to send anything on a day with nothing scheduled. The horizon there is a week rather than the page's two months, because an anniversary announced every morning for six weeks stops being read.

5. **AI Tools** (`lib/ai/tools/`): Tool-calling system with four categories:
   - **Information tools**: `addResource`, `getInformation` (RAG search), `forgetInformation`, `analyzeFile`
   - **Calendar tools**: `getEvents`, `scheduleEvent`, `deleteEvent`, `optimizeSchedule`
   - **Timeline tools** (`lib/ai/tools/timeline/`): `rememberDate`, `getTimeline`
   - **Task tools** (`lib/ai/tools/tasks/`): `addTask`, `getTasks`, `completeTask`, `scheduleTask`
   - **Table tools** (`lib/ai/tools/tables/`): `createTable`, `getTableRows`, `addTableRows`, `extractToTable`, `listTables`, `createQuickAction`, `deleteQuickAction`

**A table could be written and never read, and retrieval was standing in for the reader.** Every other table tool writes; `listTables` reports a row *count* and no rows; so the only route to a table's contents was `getInformation`, which is a top-k semantic search behind a hard `MAX_RESULTS = 5`. Asked "скільки разів Арчі прийняв апоквель" over a table holding twenty-two such rows, the assistant answered **five** — the number was the size of the cap. Asked to show the table, it recited whatever the search matched, under the column names of a *different* table it had seen earlier in the conversation. Asked again a minute later, it reported that a table of twenty-three rows had no records in it, because that time the search matched nothing. None of the three is a retrieval bug: top-k is what retrieval is for. The bug was that nothing else could answer, so `getTableRows` (`lib/ai/tools/tables/get-table-rows.ts`) does — an exact `total` computed by `count(*)`, the rows themselves keyed by column *name* rather than id, a `contains` filter as a substring over the stored JSON (the model asking for "апоквель" does not know which column holds it), and an explicit `hasMore` so a page boundary can never be read as the end of the table. `buildMessage` states in words which of the two is on the table, on the rule the briefing already follows for weekdays and lateness: anything to be concluded from a number is the application's job, because a model handed `total: 300` beside fifty rows will eventually say fifty. It deliberately does not write — not a correction, not a deletion, on the precedent that closes a task from chat and deletes it from a route.

**A search result is a sample, and it has to say so in the envelope.** `getInformation` returned a bare array. Five results and no statement of what five *was*: a model cannot tell "five matched" from "five is all you get", and there was nothing in the payload to tell it. So the answer is now `{results, returned, capped, message}`, and the message says the thing out loud — a sample of what is stored, never the complete set, never countable, never a table's contents, and here is the tool that reads the whole thing instead. The empty case is separated from the failed one for the reason `fetchEventsBetween` was: `[]` meaning both "nothing matched" and "the search did not run" is how an embedding timeout becomes "у тебе нічого не збережено". An empty result now says explicitly that it is a search result and not a census, since the assistant declaring a table empty on a failed *search* is exactly what happened. The cache still holds the results rather than the envelope — what they are is a property of the results and cheaper to restate than to store — and `KnowledgeResults` reads both shapes so a turn already on screen does not re-render as "nothing found".

**A citation is an address the application supplied, never one the model composed.** Asked where the details of a birthday were kept, the assistant answered with `https://your-link-to-the-resource/` — a link that reads exactly like the saved thing and opens onto nothing, which is strictly worse than naming the note. The prompt rule was already there and could not be followed: `getTimeline` selects whole rows, `resourceId` among them, and mapped it away, so the model was describing a note it had no address for. A date is stored twice — the row keeps the day, the note keeps the wording — so "деталі" is always the note, and `getTimeline` now hands back `/resources/<id>` per event, exactly as `TimelineAxis` links it on the page; a date the user typed straight onto the axis returns null rather than a plausible-looking guess. `analyzeFile` had the same gap with `resource.id` one line above its return, and `getWellbeing` reported on saved data with no address at all. The rule itself moved out of the Knowledge base section, where it read as a fact about `getInformation` results, into the critical rules where it covers every tool that returns a `url` — and it now names the failure it has to prevent: never an absolute `https://…` for anything saved here, never an id dressed as an anchor, never a stand-in. A result without a url is named, not linked.

**Copying rows between two tables is the operation that had no tool, so it was improvised out of a search.** Asked to move the dog's medication rows from one table to another, the assistant had `extractToTable` (which reads *notes*) and `getInformation` (which reads five of anything), so it retyped what the search returned — and the search, asked about "прийом ліків", returned the user's own wellbeing check-in: *"[2026-08-09] 20:48 · головний біль випила хелпекс"*. Their headache pill was written into the dog's table as a row that had never existed. Five rounds of correction followed, each appending more nearly-right rows and each reported as "готово, тепер коректно". With a reader in place the operation is `getTableRows` → `addTableRows` and the prompt says so; what remains is that `addTableRows` only ever appends, which the tool description and the prompt now both state, because a correction written as another row leaves both. `findDuplicates` runs *before* the insert, so it can only match a row that was already there, and reports rather than refuses — the tasks index refuses, but it has an identity narrow enough to be sure, and here two identical rows can be genuinely meant (two coffees, a table with no date column). Swallowing the second silently is unrecoverable; a visible duplicate is one click from gone. What it ends is the silence: the write it cannot prevent, it can at least refuse to call a clean save.

**A row can hold a file, and the file is a resource.** The column types were `text, number, date, boolean, email, url` — so a table about documents could name a document and never hold one, which is why a "Medical Tests" table existed with a column describing PDFs it had no way to keep. A `file` cell stores `{resourceId, name}` and the upload goes through `/api/resources/upload`, the same door as every other file: it is extracted by `unpdf`/`mammoth`, or described by the vision model when it is a photo, then chunked and embedded, so an attachment is searchable by `getInformation` the moment it lands and there is still exactly one path that puts bytes into storage. A blob URL in the cell would have been half the work and a file nothing can find — the mistake "images are stored as text" exists to prevent. The name rides beside the id rather than being looked up, so the table renders without a join, `convertRowToText` embeds "аналіз крові.pdf" instead of an id nobody will search for, and a resource later deleted leaves a cell that still says what was attached. Detaching does not delete the resource: it was read and embedded, and a row no longer pointing at it is not a reason to destroy it. `coerceValue` admits only an actual attachment, which is what makes the type safe to expose to `createTable` — the model can create a file column, cannot forge a value for one, and `addTableRows` says so rather than reporting an upload it did not do. `detectRepeatingRow` skips file columns outright: a button writes without asking and a Telegram reply is text, so the best an attachment could do in a routine is repeat one scan on every press. And `create-table.ts` had kept a private copy of the type list — the exact drift `lib/utils/table-columns.ts` was created to end, reappearing the moment a type was added — so it now imports the one list, as the new-table form's options do.

**A card answers "is this the one, and is it still in use".** The tables list showed three things and two of them were wrong. "4 columns" says how wide a table is and never what it holds; "View rows" was a `<span>` styled like a link and wired to nothing; and "Updated: August 27, 2026 at 10:06 AM" was `userTables.updatedAt`, which only `updateUserTable` touches — so a table written to every morning went on advertising the day its columns were last edited, the one date that cannot say whether it is still alive. The card now carries the row count, when the last row was written (`MAX(created_at)`, both as correlated subqueries for the reason `listTables` uses one), and the column names, which are what "4 columns" was standing in for. The list is ordered by `GREATEST(updatedAt, last row)` so daily use outranks an old rename, an empty table says "No rows yet" rather than nothing, and the delete confirmation names the number of rows about to go. `relativeTime` moved to `lib/utils/relative-time.ts`, where the dashboard's copy of it now also lives.

**A routine is a button, not a sentence said again tomorrow.** Both existing ways to write a table row go through the model — `addTableRows` reads a sentence, `extractToTable` reads a note — which is right for a fact stated once and wrong for a thing done daily: "Арчі прийняв ліки" cost a chat completion, a tool round-trip and several seconds to store six characters that never vary. A quick action (`quick_actions`, `lib/quick-actions/quick-actions.ts`, `lib/actions/quick-actions.ts`) is that row minus what the model was being asked to infer — invariant columns stored as literals, the date stamped at press time, and only what genuinely changes asked for. Pressing it calls no model: `POST /api/quick-actions/[id]/run` is session → resolve → insert, and the only remaining API cost is the embedding, which stays because a row nothing can find is not saved in any sense this app means and is three orders of magnitude cheaper than the completion it replaces. What it is deliberately **not** is a schedule — nothing knows the medicine is daily, nothing nags, nothing back-fills a missed day. The routines here are not predetermined ("today Арчі, tomorrow me, the day after a child's temperature"), and a button that assumes otherwise starts lying the first week it is wrong.

**A button that asks is a button that has failed.** The first thing the assistant did with this feature was create "Арчі — ліки" with three `ask` fields — which medicine, what dose, any notes — for a row whose every column is the same six characters every day. That is the add-row form with an extra tap in front, and it re-introduces the exact cost the feature exists to remove: the user is typing again, and a press that was supposed to be free now waits on them. The mistake is structural rather than careless — a model that has not been *told* a value reaches for `ask`, because asking is how it obtains anything — so the fix is stated in three places and enforced in one. The prompt and the tool description say the target is zero questions, that the values come from what the user just said or from the row just written into that table (that row **is** the template), and that a missing value is a reason to ask *in the conversation, once* and store the answer as a literal. `asksMoreThanItKnows` then refuses to save a button that asks for more of the row than it fills — a ratio rather than a count, since one question on a two-column table is a reading with its date stamped while three on a five-column table is a form. Its rejection message spells out the repair, because the cap that already existed (`MAX_ASK_FIELDS`) taught nothing: told "at most 3", the model simply asked for 3.

**The repetition is in the table, so nothing has to notice it.** The deeper fault was upstream of any of that: a button existed only when someone thought to ask for one, and the prompt's answer was to tell the model to spot the pattern itself — "two or three near-identical rows into the same table is the signal". That instruction could only ever fire inside a conversation that happened to contain the rows, which is the one place the evidence is *not*: the user writes the same row every day, each time in a fresh chat, and the fortnight of identical rows sits in the table where nobody looks. `detectRepeatingRow` (`lib/quick-actions/detect.ts`) looks. It groups the recent rows on the columns that do not vary, and a group of three on three different days is a routine: the repeating values become `fixed`, a date column that tracks the day the row was written becomes `today`, and a column that differs every time *and is usually filled* becomes the one `ask` — which is `MAX_SUGGESTED_ASKS`, stricter than the guard above, because an offer nobody asked for has to be a button worth pressing without reading it. `addTableRows` runs it after writing and hands the template back in its own result, so the offer arrives at the moment the user has just done the thing by hand again; the model passes those fields through rather than re-deriving them, and the prompt bullet telling it to count rows by eye is deleted rather than left standing beside a mechanism that does it properly.

**And once the table notices, the model must stop noticing too.** Leaving `createQuickAction` described as "call it when a record repeats" beside a detector that reads the rows meant both fired at once: one conversation about Арчі's pills produced a model-made button — evening dose, and asking for the *date*, which is the one value the clock already knows — while the table page offered the morning dose it could see in seven rows across seven days. Two standing objects on the user's screen where none had been asked for, and the worse of the two was the one the model volunteered, because it was inferring a template from a conversation while the other read it off the data. The prompt and the tool description now name two triggers and no others — the user asks in so many words, or `addTableRows` said NOTICED and they said yes. The tool is kept rather than deleted: "зроби кнопку" has to work on the day someone says it, and the detector cannot answer for three days.

A routine already covered is now told to the detector rather than filtered out of its answer, which is what makes offering the *second* routine in a table possible at all. `detectRepeatingRow` returned the biggest group and the caller dropped it when a button matched — but the biggest group is the biggest group tomorrow as well, so accepting one offer silenced the page permanently, with the evening dose still being typed by hand every night. It now walks the groups in size order and answers with the first that no button covers.

Three details are load-bearing. Days are counted from the row's own date column when there is one, not from `created_at` — "я всі ці дні давала Арчі ліки, заповни таблицю" writes a fortnight in one afternoon, and counting when the rows were *written* would read that as a single event and decline to notice the very routine being described. A date column only becomes a stamp when the rows show it tracking either the day they were written or a different day each time; otherwise an expiry date would be silently overwritten with today's on every press. And `covers` is one function shared by the detector and its two callers, so "this routine already has a button" cannot be answered two ways — comparing labels would not survive the user renaming one.

**An offer is a reading, and a reading gets one chance to be corrected.** Two things about the offer were wrong in the same way: it presented what the rows say as though it were already a decision. The face was `values.join(' — ')` cut at `MAX_LABEL_LENGTH`, which turned a dog's daily dose into `Create "вранці — апоквель — у відповідності з пр"` — the third value is a notes column holding the same standing instruction every day, which identifies nothing and is exactly what pushed the name past its width, and a `slice` finished it mid-word. `labelFor` therefore builds the name from the values that read as *names* (`NAME_LENGTH`, three at most) and drops what does not fit whole rather than cutting it, falling back to a word-boundary clip with an ellipsis only when there is nothing shorter to use. And `RoutineOffer` now opens: the label and every `fixed` value are editable in place before the button is accepted, with the date stamp and the questions shown read-only because what they hold is decided at press time. A value cleared drops its column from the template rather than writing a blank on every press — an empty cell reads as "recorded, and there was nothing" — and a template with nothing fixed left cannot be created at all, which is `asksMoreThanItKnows` said in the client's own terms.

Editing is what forced `signatureOf` out. Identity by exact fields answered "does a button already cover this?" only while the button was the template verbatim; a user who drops the notes column or shortens a value creates a button that no longer matches the rows it came from, and the page goes back to offering a routine that has had a button on it since Tuesday — daily, until the old rows age out of `MAX_ROWS_SCANNED`. `covers` asks the question the accepting was an answer to: every field the button *writes* matches the routine's, and the columns it leaves out are the ones the user chose not to keep. Fixed values match on case, spacing and containment past `MIN_CONTAINED_LENGTH`, so "ліки" reworded as "ліки (апоквель)" is the same routine while "вранці" and "ввечері" remain two. A button carrying no fixed value of its own covers nothing, since a date stamp and a question describe every routine in the table equally well.

`kind` is `fixed` | `today` | `now` | `ask`. The two date kinds are separate rather than read off the column's type, on the timeline's `precision` reasoning: how much of a date is meant is a decision, not something to infer — a medication log wants the day, a temperature reading is worthless without the hour. `today` writes a bare `YYYY-MM-DD` and `coerceValue` now leaves such a string alone, because parsing it through `Date` makes it UTC midnight and prints as the day before west of Greenwich. Both are computed in `timezoneFor(userId)`, never the server's clock: at 01:30 in Kyiv the server is still on yesterday, and a dose filed a day early is never noticed. An unanswered `ask` **stops the write** rather than storing a blank — an empty column reads as "measured and found nothing", and no later view can tell the two apart. A field naming a column the table no longer has is skipped instead of written under a dead key, since columns can be renamed and deleted from the editor while a button still points at them.

**Undo, not confirm.** The button's whole value is that one tap ends it, and a confirmation doubles the interaction on the ninety-nine presses that were right to save a click on the one that was not — so the write happens and an undo stands for a few seconds (web toast, Telegram inline button). It deletes only a row *this* button wrote, checked against `metadata.quickActionId`, so a guessed row id cannot be laundered through it; and the usage stamp is then recomputed from the rows that remain rather than decremented, because decrementing gets `lastUsedAt` wrong — undoing this morning's press should leave the button showing yesterday's, and only the rows know when that was. `lastUsedAt` exists to answer the question a person actually has in front of a daily button (*did I already give him the pill?*), which is why it is read back onto the button face and not kept for analytics.

**The label is the identity, on both surfaces.** `UNIQUE (user_id, lower(btrim(label)))` stops the assistant creating a second "Арчі — ліки" it cannot tell from the first, and it is what makes the Telegram flow possible at all: a callback press carries no conversation, so a button that asks for a value sends a `force_reply` prompt with its label in guillemets and the reply is matched back on that. Hence `sanitizeLabel` — `sendMessage` strips Markdown on the way out, so a label written "Арчі *ліки*" would arrive as something else and match nothing; sanitising once on write is what makes the round-trip safe by construction rather than by every reader remembering to normalise. Several values are asked for in one comma-separated reply (`splitAnswers`), with the last field keeping any trailing commas because it is usually the free-text note; with one question there is no split at all. `MAX_ASK_FIELDS` is 3 — past that, pressing a button is not faster than the table's own add-row form. Callback data uses two more namespaces beside the notification `n:` one, and the parsers are mutually exclusive by test: a notification's "save" read as a quick action would write a row.

`MAX_QUICK_ACTIONS` (12) is the same reasoning as `MAX_DIRECTIVES` — past a dozen this stops being a row of buttons pressed without reading and becomes a list to search, at which point typing the sentence was faster. Hitting the cap is reported, never resolved by evicting the oldest. Buttons render in creation order rather than most-recently-used, deliberately: one pressed every morning should be in the same place every morning, and a list that reshuffles under a thumb is how the wrong row gets written. Deleting a button touches nothing it wrote — the rows are the record — and needs no tombstone, unlike `entity_exclusions`, because nothing recreates a quick action behind the user's back. Managing them lives on `/tables/[id]` and not on the dashboard, where a delete control beside a daily button is a mis-tap waiting to happen.

The column type list moved to `lib/utils/table-columns.ts` as part of this: it had two hand-maintained copies (`tableColumnSchema`'s `z.enum` and `create-table`'s `COLUMN_TYPES`), which is the exact drift `metadata.type` already went through, and the quick-action bar is a client component that needs the list and the coercion without dragging drizzle into the browser — same reason as `lib/utils/uploadable.ts`.

6. **Tasks** (`lib/db/schema/tasks.ts`, `lib/tasks/`, `lib/actions/tasks.ts`, `app/tasks/`, `lib/ai/tools/tasks/`): the things that have to be done, with a deadline or without one.

**A deadline and a day of work are different dates, and keeping only one of them is wrong in one of two ways.** Keep only the deadline and every task shouts on the day it is due and is silent for the fortnight when it could actually have been done; keep only the working day and nothing knows Friday is the last chance. So `due_on` is the last acceptable day and never leaves this app, while `scheduled_for` is the day the user committed to doing it — and committing is what writes a Google Calendar event, because at that point it really is a plan for a day and belongs beside everything else claiming that day. That boundary is the whole design: the calendar stays a record of days the user agreed to spend rather than a pile of everything outstanding. A task carrying neither date is not broken, it is the ordinary "sometime" item that a list of only dated things has nowhere to put — and the page shows all four groups at once rather than only today, because a deadline a fortnight out is exactly what you want to see while there is still a choice of days to do it on.

**This layer was designed into the app before it existed.** `metadata.needs` has been extracted from every note for months with **zero** read consumers, and `DATE_EXTRACTION_RULES` refuses deadlines from the timeline in as many words — "a deadline is a *task*… `needs` already carries it in metadata waiting for a tasks layer to read. Putting it on the axis makes the axis a worse to-do list." So deadlines landed nowhere at all: not the timeline (refused), not the calendar (not an event), not tasks (absent). `listTaskSuggestions` is the consumer, and it computes rather than stores — a suggestion is a *reading* of a note, and materialising readings means keeping them in step with notes that get edited, merged and compacted. `task_suggestions` records only decisions, accept and dismiss alike, since both mean "handled" and only provenance differs. Nothing lands automatically: extraction is liberal by the same design that puts a greeting in the entity graph, so "хочу колись вивчити React" arrives looking exactly like "подати заяву до 17.08".

**All-day and timed are two different promises, and Google is told which.** A day with no hour becomes an all-day event marked `transparency: 'transparent'` — it holds no time, so it must not veto a meeting and must not appear in the briefing's schedule beside its own line in the tasks block. A day with an hour is an ordinary opaque event. Note the asymmetry that makes the Free flag necessary at all: `nonBlockingReason` already returns `'all-day'` before it looks at transparency, so conflicts were never the problem — `fetchEventsBetween` was, since it filters on `isTimeBlock`. Three fixes had to land in `lib/services/calendar.ts` first, because the wrapper could express none of this: `createEvent` hardcoded `{ dateTime }` so all-day was unreachable; `patchEvent` did too, so an event could never be converted between the two without a delete-and-recreate that changes the id the task row holds (it now sends the unused field as an explicit `null`, which is how Google is told "and not that one"); and `deleteEvent` re-threw on 404/410, so a user who removed the event on Google's side could never unschedule the task pointing at it — every attempt failed and the row kept a dead id forever. Writes go to `'primary'` and never through `scheduleEventTool`, whose `moveIfExists` would fuzzy-match two similarly-named tasks within ±72h into one, and which needs a session the cron path does not have.

**Rolling a recurrence forward is anchored to the schedule and always lands past today.** Miss three days of vitamins and the next dose is tomorrow, not the day before yesterday: a recurrence that re-emerges already overdue can never be caught up with, and a list that permanently accuses is a list that gets ignored. `nextDueDate` always recomputes from the *original* due date rather than stepping from its last answer, or one February turns a "31st of the month" task into a 28th-of-the-month task permanently. History comes from `task_completions`, one row per closing — a single rolling row otherwise has no past, and "чи приймала я вітаміни цього тижня" has no answer. Its `UNIQUE (task_id, completed_on)` is not tidiness: Telegram's `clearReplyMarkup` is best-effort, so the same button really can fire twice, and rolling twice would silently skip an occurrence. What is deliberately **not** expressed is "every two weeks from whenever I last did it" — a real and different intention, one field and one migration away.

**Identity is open-only, and fails open.** `tasks_open_identity_unique` is `(user_id, lower(btrim(title)), coalesce(due_on, DATE '1970-01-01')) WHERE status = 'open'` — partial *and* expression, so drizzle can express neither and it lives only in migration 0027 (never `db:push` this table, same hazard as `timeline_events`). Partial because a task done in March and raised again in August is a new one, and refusing it would be indistinguishable from the save silently failing. `coalesce` because Postgres treats NULLs as distinct and two undated "подзвонити в садок" would otherwise both insert. It catches case and outer whitespace and deliberately not internal whitespace or word order — a visible duplicate can be deleted, a silently swallowed task cannot be recovered because nobody knows it was ever asked for. Drizzle only permits the bare `onConflictDoNothing()` here (an explicit target is built from column names and cannot name an expression), so the read-back after a rejection must match all four parts of the index by hand, the status predicate included, or the model is handed a completed task and told "already have it".

**Closing is a tool, deleting is a route.** The wellbeing and timeline line, drawn for the same reason: closing is reversible — the row stays, `reopenTask` puts it back, the completion log keeps its record — and deleting is not. An ambiguous name is reported back rather than resolved, on the `matchDirective` precedent and for a sharper version of its reason: closing the wrong task removes something that still needs doing from the only list tracking it, and the user finds out when the deadline has passed.

**Overdue tasks are asked about one message at a time.** Buttons under the briefing itself do not survive contact with the code: `clearReplyMarkup` wipes a keyboard entirely and does so deliberately, so that "Save" on a week-old briefing cannot file a second copy — pressing one task's button would retire every other task's too — and `snooze` rebuilds the notification from its text with a hardcoded action list, so the lines would come back with no buttons under them. One short message per overdue task sidesteps all of it: each carries its own keyboard, a press clears only its own, and none of the notification machinery changes. `t:` is the fourth callback namespace beside `n:`, `q:` and `qu:`, and the task id rides in `callback_data` rather than being read back off the message text — which is exactly what lets a press identify its own task. "Tomorrow" moves the *deadline*, since that is what makes the task overdue; nothing moves a date without a press. Fixing this also closed a latent bug: `handleCallbackQuery`'s `runWithUser` never supplied `resolveAccessToken`, so any button touching Google would have thrown `Unauthorized`.

**The briefing block is assembled, and survives an unreadable calendar.** `taskLines` prints lateness the application computed — the rule this file already follows for `scheduleLines` and `dateLines`, and it matters more here, since a briefing claiming a deadline passed two days ago when it passed five is worse than one saying nothing. Tasks come from our own table rather than from Google, so they go out under `calendarUnreadable` for the same reason saved dates do. A task already committed to today is deliberately absent from the block: it has a calendar event and is therefore already in the schedule above, and printing it again would show one commitment twice under two headings.

7. **Push / notifications** (`lib/push/`, `app/api/push/`): Proactive briefings, insights, and a weekly retrospective. Notifications are written to the `notification_queue` table first (durability), then delivered two ways: precise-time callbacks via Upstash QStash (`lib/push/qstash.ts`) and a periodic Vercel Cron sweep (`vercel.json` → `/api/push/scheduled`, `/api/push/drain`, `/api/push/retrospective`). Cron- and QStash-invoked routes carry no session and authenticate with `CRON_SECRET` via `validateCronSecret` (`lib/push/utils.ts`); they must therefore be listed in `middleware.ts` `publicPaths`. `sent_notifications` is a dedupe ledger so the same briefing isn't sent twice.

**"Push" is the schedule, not the transport.** Delivery is Telegram, through the one door in `lib/push/deliver.ts`; Web Push is gone, along with `push_subscriptions`, the service worker, the VAPID keys and `/api/push/{subscribe,vapid-key,send,action}`. A subscription bound notifications to one browser profile, expired without telling anyone, and on iOS existed only for an installed PWA — so briefings were reliably generated and unreliably seen. What makes an account reachable is now `users.telegram_chat_id`, which is also what the dispatchers select on; before, they joined `push_subscriptions` and silently skipped everyone who had never granted browser notifications. The names (`lib/push/`, `/api/push/*`) stay because QStash schedules point at those paths — renaming the routes means re-creating every schedule.

**The briefing is assembled, and nothing in it is generated.** Every line is built by the application from the events, dates and tasks it was given (`scheduleLines`, `dateLines`, `taskLines` in `lib/push/briefing.ts`), and the morning pass makes no LLM call at all. There used to be one model-written sentence above the list, and it was narrowed twice for inventing things: first for padding a one-event day with atmosphere ("the day will be festive, which may get in the way of plans"), then for announcing that "between the daily meeting and the maths class there is only an hour" on a day where those two sat six hours apart — the only one-hour gap that day belonged to a different pair entirely. The second failure is why it was deleted rather than narrowed a third time. The prompt asked for "a clash, a tight gap, a long unbroken stretch" while handing over nothing but a list of start times, so the sentence it commissioned *was* arithmetic over dates — exactly what `weekdayOf`, `dateLines`, `taskLines` and `isSlotWithinHours` were each fixed by moving into the application, except that here there was nowhere to move it to: a gap is only worth mentioning if something judges it worth mentioning, and nothing computes that. The ban on consequence in the same prompt could never hold either, because a prompt that names a tight schedule as the topic leaves the sentence nowhere to end but a consequence. The old 180-character ceiling was a browser-notification constraint and went earlier; `MAX_EVENT_LINES` and `MAX_TITLE` are what remain. The retrospective still generates — it reflects on a week that has happened, which is a different job from asserting something about a day that has not.

**`fetchDayNotes` now has one consumer, and its three cuts still earn their keep.** It was built for the deleted lead sentence and is kept for the proactive scan (`insight-scan.ts`), which matches notes against who the user is meeting; `briefing-run` retrieves once and passes them there only. The cuts stay because the scan is just as capable of asserting something unprompted. Retrieval returns its top *k* because *k* is what it was asked for, not because *k* things were relevant — handing that list on under the heading "notes that may be relevant" turned a day with one all-day birthday into a briefing that reported the user's mood and their coffee from a check-in three days earlier. So: a similarity floor, higher than `getInformation`'s and not admitting lexical-only hits the way that one does — there a marginal hit answers a question the user asked and can be ignored on sight, here it becomes an unprompted assertion about their morning, and the query is a calendar title rather than a question ("День народження" reduces to a prefix matching half a Ukrainian base on a word meaning nothing about today). Wellbeing check-ins are dropped outright, on genre rather than on age, since one from this morning is no better: the tracker records and does not assess, and a paragraph narrating the user's mood back at them at breakfast is assessment, on the most sensitive content in the base. And what survives carries the day it was written, because undated a note from Tuesday reads as this morning — which is exactly how a past mood came back in the present tense.

The prompt is what produced the prose around it. Asked for "two or three sentences" and told to lead with a clash, a tight gap or the commitment the day turns on — all of which presuppose a busy day — a model given one entry has to invent one, and it padded to `MAX_HEADLINE` with atmosphere: the day would be festive, which might get in the way of plans. So length is now a property of the day, an empty answer is explicitly the right answer when the list below already says everything, and the ban covers mood, atmosphere and consequence rather than only invented events — the failure was fabricated characterisation, which "never invent events or details" did not reach. `cleanHeadline` reads a model's near-misses at silence ("—", "N/A", "(none)") as the silence they were meant to be, since printed above the schedule each is a line that looks like a bug.

**An unreadable calendar is not an empty day, and a declined event is not a commitment.** `fetchEventsBetween` returned `[]` both when Google answered "nothing" and when it refused to answer, swallowing every rejection through `Promise.allSettled` without so much as a log — so an account whose refresh token Google had expired got five consecutive mornings of "нічого не заплановано — календар вільний", which is the most confident possible way to be wrong. It now logs each failed calendar and *throws* when every calendar failed, on the same reasoning that makes `listCalendars` throw; a partial failure still returns what was read, because one unreadable shared calendar should cost that calendar and not the morning. `generateBriefing` takes `BriefingEvent[] | null` to carry the distinction the whole way — `[]` is a claim about the day, `null` is the absence of one — and `briefing-run` maps both failures onto `null`, the missing token included, since a refresh token Google has revoked is exactly how this presents. Saved dates still go out under it: they come from the timeline rather than from Google, and a birthday is the one thing a broken calendar must not eat. Separately, an event the user declined stays on their calendar and Google keeps returning it; `isDeclined` had lived in `insights.ts` and guarded only the proactive scan, so the briefing printed a week of meetings its user had said no to. It moved beside `EventAttendee` in `calendar-window.ts` and was applied by `fetchEventsBetween` itself — after the dedupe, since only the copy on the user's own calendar carries `responseStatus` — because a rule that has to be remembered by three callers gets remembered by two. The third caller was `getEvents`, and it did not remember: the whole fix landed on the notification path while the chat kept listing declined meetings as commitments. So `isDeclined` and `EventAttendee` now live in `lib/utils/calendars.ts` next to `isTimeBlock`, dependency-free for the reason written there, and `calendar-window.ts` re-exports them so its existing importers keep their address.

**`getEvents` was the path all three calendar rules had been fixed around.** It is the tool behind every schedule question in chat and Telegram, and it had none of them. Declined invitations were listed. Nothing de-duplicated, so an event on both the user's calendar and a shared one appeared twice — and that ordering matters for more than tidiness: filtering declined per calendar would drop the user's own copy, the only one carrying their `responseStatus`, and keep the shared calendar's status-free twin, so the de-duplication is what makes the filter correct. A rejected calendar contributed nothing, logged nothing and threw nothing even when *every* calendar failed, which is the same "most confident possible way to be wrong" that cost the briefing five mornings; `CalendarUnreadableError` is thrown in that case and passed through the outer catch unchanged, because collapsing it into the generic tool failure is precisely how an unreadable calendar becomes indistinguishable from an empty one. The hand-built `['primary', ...followed]` list is gone in favour of `getCalendarIdsForUser`, which drops a followed calendar that is the user's own address — Google answers for it under both names, so following yourself fetched every event twice.

**One reply, two surfaces, and only one renders Markdown.** `sendMessage` (`lib/telegram/api.ts`) sends without `parse_mode` deliberately — MarkdownV2 requires a dozen characters escaped everywhere and rejects the whole message when one is missed, so an unstyled message that always arrives beats a styled one that intermittently 400s. The consequence went unhandled for as long: every `**` and `###` the model wrote reached the bot as literal punctuation, so a schedule arrived as `### Завтра` over `1. **Робочі години**`, noisier than the plain text it was decorating, while the web chat rendered the same reply properly. `stripMarkdown` removes the syntax rather than translating it, running after `flattenMarkdownLinks` because that one rewrites the bracket form this leaves alone. Emphasis is unwrapped only where the marks hug the text, so `3 * 4 * 5` survives; list markers stay, because in plain text a list still reads as one. Schedule layout is then a prompt rule rather than an assembled block — `getEvents` answers "чи вільна я о 15?" as much as "що цього тижня?", and only the second wants a list — but the pieces the rule needs are supplied, not computed by the model: `Day` and `At` are in the line ready to print.

**Free time is not tracked, and the reason is not that it was hard.** `lib/utils/free-time.ts` computed a `[Free]` line per day — each open window, its length, the day's total — and `eventsToModelOutput` appended those lines to every `getEvents` result. Two things were wrong with it. The first is that nobody asked: the lines rode along under every "що в мене сьогодні", so a plain schedule question came back with a free-time total appended, which is commentary on someone's day rather than an answer. The second is that the number was wrong. `occupies` excused a block marked Free by calling `isTimeBlock(e)`, which reads `transparency`/`eventType` — and `get-events.ts` flattens those into a single `timeBlock` boolean at the door and carries neither field onto `ToolCalendarEvent`. So the check was structurally always false, a standing "Робочі години 08:30–18:00" was counted as busy, and a day with two evening events reported 2 год 30 хв free. It typechecked in silence because every field `FreeTimeEvent` wanted beyond `allDay` is optional, and the unit test passed because it built its fixtures with `transparency: 'transparent'` — the shape this path never produces. `attendees` was dropped the same way, so the declined-invitation exemption was dead too. The module, its test and the prompt rule telling the model to read the lines off are all gone; the system prompt now says free time is not tracked and that nothing may be derived from the times in a result, because deleting the tool line without saying so is an invitation to subtract the events in the reply, and that answer has no test behind it at all.

**The weekday is computed, never derived.** `getEvents` handed the model a bare ISO timestamp per event, so naming the day it fell on was arithmetic left to the model — and asked what was on this week it answered "18 серпня (четвер)" for a Tuesday and shifted every day after it. `weekdayOf` (`lib/ai/tools/events/get-events-format.ts`) puts `Day: Tuesday` in the line, on the rule the briefing already follows: anything derived from a date is the application's job, because a model asked to restate one eventually restates it wrong, and a schedule naming the wrong day is worse than one naming none. It reads the first ten characters rather than parsing through `Date`, since that prefix is already local to the event's own offset while `Date` answers in the server's zone. The same line now carries `Note: marked Free` for a `timeBlock`, which is the chat-side half of the entry below — the push path drops those events, but "що в мене цього тижня?" is a question about the calendar, so here the block is labelled rather than hidden, and the frozen byte-identical line test was updated on purpose rather than worked around.

**A block is not a commitment.** `isTimeBlock` (`lib/utils/calendars.ts`, which imports nothing, so both the raw Google shape and the normalized one can pass) reads Google's own answer: `transparency: 'transparent'` — the "Free" toggle — or `eventType: 'workingLocation'`. The writing path learned this first and the notification path did not, so a standing "Working hours 08:30-18:00" was counted as a commitment: listed among the day's tasks, inflating the count in `thingsToday`, and reported by `findConflicts` as a clash against every meeting inside it — three overlap alerts in one morning, each telling the user that working during working hours is a problem. It is filtered in `fetchEventsBetween` beside `isDeclined`, and both now live in this file for the reason written there: a rule that has to be remembered by three callers gets remembered by two. `schedulable` keeps its own guard anyway, since `scanDay` takes its events as an argument. Focus time and out-of-office are deliberately not excused — they hold the time, and only the Free flag says otherwise. Note the limit: a working-hours block that is *not* marked Free is indistinguishable from a meeting, and nothing here matches on a title.

**Notification language is `users.locale` (`uk` | `en`), and only notifications.** All copy — titles, deterministic fallbacks, durations, and the `writeIn` line appended to each generation prompt — lives in `lib/push/copy.ts`; the web UI stays English, because a notification is read where the bot speaks and a settings screen is not. Ukrainian's three plural forms are why counts go through `pluralUk` rather than a ternary. Clock times are `en-GB` in both languages on purpose: digits are digits, and a locale-shifted format only makes the briefing's column of times ragged. An unrecognised stored locale resolves to the default instead of throwing, since it would otherwise fail a cron run that has already paid for an LLM call.

Notification buttons are Telegram inline keyboards. `callback_data` is capped at 64 bytes and there is no session cookie on a press, so an action is a name plus a number (`lib/telegram/callback-data.ts`) and everything else is read back off the message text it was attached to — which is why `renderNotification` joins title and body with a blank line and `splitNotification` cuts on it. `handleCallbackQuery` (`lib/telegram/callbacks.ts`) resolves the user from the chat id exactly as an ordinary message does, then strips the keyboard so a week-old briefing can't be saved twice.

**Cron cadence lives in QStash, not `vercel.json`.** The Hobby plan rejects any cron firing more than once a day, and these endpoints ask "who is due right now?" rather than planning a day ahead — so a daily sweep alone drops nearly every briefing. QStash schedules call the same paths with the same `CRON_SECRET`; the entries left in `vercel.json` are a once-a-day backstop for when QStash is unreachable. Changing a briefing's cadence means editing the QStash schedule, not `vercel.json`.

8. **Telegram entry point** (`app/api/telegram/`, `lib/telegram/`): A second surface onto the same assistant. `/api/telegram/webhook` validates the `x-telegram-bot-api-secret-token` header, then hands the update to QStash and returns 200 immediately (Telegram redelivers anything it doesn't get a prompt answer for); `/api/telegram/process` is the callback that actually runs the agent, authenticated with `CRON_SECRET`. Both are in `middleware.ts` `publicPaths`; `/api/telegram/link` is not, because issuing a link code requires a session. Voice notes are transcribed by Groq's `whisper-large-v3-turbo` (`lib/telegram/transcribe.ts`). Chat history is shared with the web chat — same `conversations` row — so a thread continues across surfaces.

**One bot serves many people, and only in private chats.** The binding is a per-user column (`users.telegram_chat_id`, unique), so every account that can sign in can link its own chat to the same bot; `findUserByChatId` resolves the owner per update and `runWithUser` scopes the agent to them. The gate on all of it is `ALLOWED_EMAILS`, since a code can only be issued from an authenticated session. That same design is why group and channel updates are dropped (`isPrivateChat` in `lib/telegram/process.ts`): a chat id is the entire identity here — nothing asks *which* member is speaking — so a linked group would hand every current and future member the owner's knowledge base and calendar. `/unlink` lives on the bot side rather than only in settings, because someone who was invited to this instance may never open the web app again and still needs to stop the bot answering as them. For the same reason user-facing failures never name an env var: whoever is typing may be a guest on someone else's deployment, so the setting goes to the log and the chat gets "write to me in text instead".

Photos and documents (`lib/telegram/media.ts`) are **saved, not discussed**: they arrive with no question attached, so `processUpdate` ends the turn on them rather than feeding a wall of OCR to the agent and burning its step budget. The reply quotes back what was actually read, because vision output is the one thing here the user cannot verify against a source — a misread figure on a receipt has to be caught while the paper is still in hand. A caption becomes the title. Telegram re-encodes photos to JPEG, so HEIC never reaches this path; images sent *as documents* (what you do when compression would make a page of text unreadable) are detected and routed to the image path rather than rejected.

`/q` prints the quick-action buttons (`lib/telegram/quick-actions.ts`) — a command rather than a persistent reply keyboard, which would otherwise sit under every message including the ones asking a question. This is where the feature earns most of its keep: the routines it records happen with a phone in hand and nowhere near a browser. Unlike a notification's keyboard, a pressed quick-action panel keeps its buttons — it is a control panel, not a one-time decision, and tomorrow's press should not need a new `/q`. A reply to a `force_reply` prompt is intercepted before the agent runs, because "37.2" sent to the model comes back as a polite enquiry about what that means.

`/google` is the fourth command beside `/start`, `/unlink` and `/q`, and the only one that exists to repair something: it checks whether Google still honours the stored permission and, when it does not, hands over the numbered steps and a link to Settings → Google. See "A refresh token is not forever" under Request context — the reasoning is there because three surfaces share it.

9. **Wellbeing tracker** (`lib/db/schema/wellbeing.ts`, `lib/wellbeing/`, `lib/actions/wellbeing.ts`, `app/health/`): mood, energy, sleep and symptoms, logged conversationally and charted.

**State is stored twice, on purpose.** The scales go to `wellbeing_entries` where a chart can read them; the user's own words also go to `resources` (linked by `resource_id`) where retrieval can. Neither half does the other's job — no amount of embedding turns a paragraph into a trend line, and no column answers "коли востаннє боліла голова?" the way a semantic search does. The row is written first and the note indexed after: the measurement is durable and costs one INSERT, indexing costs an embedding call that may fail, and a flaky OpenAI call must never cost the user the number. This is also why `logWellbeing` exists as a separate tool rather than letting `addResource` take it — that tool is instructed to save personal facts proactively and will otherwise swallow "болить голова" as prose.

**One row per check-in, never one per day.** "Зранку добре, після обіду розболілась голова" is two measurements and the time between them is the part worth seeing; an in-place update would keep only the second. Folding into one point per day happens at read time in `lib/wellbeing/aggregate.ts`, where the rules are visible and reversible: mood and energy are averaged over the day, sleep is *not* — it describes one night, so a second value is a correction and the later one wins, where averaging 6 and a corrected 6.5 would produce a night nobody slept. Days with no check-in stay in the series as empty points so the chart breaks the line rather than drawing through the gap — the missing stretch is usually the bad one. Symptoms are counted per day, not per mention, so complaining volubly on one afternoon doesn't outrank a symptom that persists for a week.

**A symptom is only trackable if it lands on the same label twice.** Left to itself the model names things fresh each time — "голова важка й мутна" came back as `["важка", "мутна"]` — so the frequency chart filled with one-off adjectives and reported that nothing ever recurs, which is exactly backwards. Two fixes, both needed: the `symptoms` parameter description demands noun phrases naming the complaint (bare adjectives and severity words belong in `note`), and `lib/wellbeing/symptoms.ts` matches each incoming label against the vocabulary this user has already used, keying on stems rather than text. The stemmer is crude on purpose — strip one inflectional ending, strip a trailing adjectival `-н-`, fold `і`→`о` for the closed-syllable alternation — which is what makes "головний біль", "болить голова" and "головного болю" one bar instead of three. The display name is always a spelling the user's own check-in produced; synonyms ("втома" / "виснаження") are deliberately never merged, because that is a judgement call and collapsing it silently destroys a distinction they drew.

Two labels match either exactly (stems sorted — so word order does not matter) or as a **specialisation**: one is the other said at greater length, "білий шум" inside "білий шум в голові". The specialisation test is an ordered subsequence and needs at least two stems on the shorter side, both of which are load-bearing. Unordered containment matched "білий шум в голові" against "головний біль", because a stemmer this crude cannot tell "біль" from "білий" — both reduce to `біл` — so the two labels really do share `{біл, голов}`; reading them in the order they were said pulls the pair apart. The two-stem floor is what stops "нудота" being swallowed by "нудота після їжі", which is a narrower claim, not the same one. `pnpm wellbeing:canonicalize [--dry]` re-runs the matching over check-ins written before a rule was loosened, replaying each user's vocabulary oldest-first so a later label folds onto an earlier one and never the reverse.

`localDate` is denormalised because charts group by local day and re-deriving that from a UTC instant applies today's offset to an entry made before a DST change. `sleep_minutes` is an integer because "7 год 20 хв" as a float comes back out as something else. The 1–5 scale is enforced in zod *and* as a SQL CHECK: a 7 on a 1–5 axis is not a bad reading, it is a broken chart. `sleepMoodSplit` returns null until both buckets hold five days, because a split computed from two nights reads exactly like a finding.

Charts are hand-written SVG (`app/components/wellbeing/charts.tsx`) — a charting library would be the largest thing in the client bundle for two charts of at most a year of single-value points. Colours are DaisyUI channel variables so the theme switcher still works. `WELLBEING_SCALE_MIN`/`MAX` live in `lib/wellbeing/scale.ts` rather than beside the column they constrain, and the schema imports *them*: the charts are client components, and importing from the schema would drag drizzle and every table definition into the browser (same reason as `lib/utils/uploadable.ts`).

**The tracker records; it does not assess.** The system prompt forbids diagnosis, causal explanation and medical advice, and the page says so in as many words. Deletion is an API route, not a tool — a mislogged number is corrected by looking at the row, and a model choosing which measurement to drop is a failure mode this data cannot afford. Health is also the most sensitive content in the base, which makes the Blob caveat above load-bearing: photos of lab results or prescriptions do not belong on the image path, where an unguessable public URL is the only protection.

10. **Response preferences** (`lib/db/schema/directives.ts`, `lib/directives/`, `lib/actions/directives.ts`, `app/api/directives/`, `app/settings/ResponsePreferences.tsx`): standing instructions about how the assistant should answer — language, length, format, what to skip.

**These are prepended, not retrieved, and that is the whole point.** Preferences were already storable: `addResource` classifies them as `metadata.type: 'preference'` and embeds them, and the system prompt tells it to do so proactively. But a resource only surfaces when `getInformation` searches for it, and nothing searches before answering "що в мене завтра?" — so "відповідай коротше" sat in the knowledge base being perfectly findable and never once applied. `assistant_directives` rows go into the system prompt on every turn instead, which is why they need a bounded, listable home rather than a flag on a resource: a note is prose that is inert until something matches it, a directive runs on every request across both surfaces and a wrong one degrades every answer invisibly.

`agentOptions()` is async for this reason — the system prompt is now per-user. Building it there rather than at each entry point is what makes a preference set in the web chat hold in Telegram without either surface knowing the feature exists. A failed read degrades to an empty block rather than throwing: a lost preference costs tone on one reply, an exception costs the reply.

`MAX_DIRECTIVES` (20) and `MAX_DIRECTIVE_LENGTH` (200) are the difference between a preference memory and a slowly rotting system prompt — these compete with the user's actual question for attention, and long rules are the ones that contradict each other. Hitting the cap is reported to the model, never resolved by evicting the oldest: the user typed each of these. The length cap is in zod *and* as a SQL CHECK, on the wellbeing precedent. Both constants live in `lib/directives/directives.ts` rather than beside the column, because the settings panel is a client component (same reason as `lib/wellbeing/scale.ts`).

Editing is in place and settings-only. Delete-then-add would be equivalent except for order, and order is not decoration here — the list is rendered oldest-first into the prompt, so retyping a rule to fix one clause would silently send it to the bottom. It is also the common repair: a standing instruction is usually right except for being one word too broad. The duplicate check excludes the row being edited, or every edit would be rejected as already saved. An edited directive always becomes `user`-sourced whatever it was before — once someone rewrites the model's reading of their habit, the "you didn't ask for this" badge would be a lie. No tool for it: the chat repairs a rule by dropping it and stating the new one, which is the same two sentences a person says anyway and does not need the model resolving "change the third one" against a list it cannot address by id.

Deleting is by description, not by id: quoting an id back would mean rendering nanoids into every prompt to serve the rarest action. The price is `matchDirective`, which shares its similarity function with the duplicate check — so "that's the same instruction" and "that's the instruction you meant" can never disagree — and returns `ambiguous` rather than a best guess, because dropping the wrong standing rule is the one failure here nobody notices at the time. Near-duplicate detection is deliberately dumber than the symptom matcher: symptoms are matched blind and charted, directives top out at twenty on a settings screen where a survivor is one click from gone.

The block renders *below* the assistant's own rules and says in as many words that preferences never override them. Directives arrive through a tool the model can call itself, so nothing must be able to talk its way into switching off the medical or confirm-before-writing rules. `source` (`user` | `inferred`) exists only for the settings screen — both are followed identically, but an inferred rule is the model's reading of a repeated correction, and someone puzzled by an answer needs to see that they never asked for it.

### Request context

Tools used to read the NextAuth session directly, which tied them to a browser cookie. They now resolve the user through `lib/auth/context.ts`, an `AsyncLocalStorage` store that falls back to `auth()` when nothing was pushed onto it. The web path is therefore unchanged, while cookie-less callers (Telegram, cron) wrap their work in `runWithUser` and supply the user themselves. Google access tokens for those callers come from `lib/auth/google-token.ts`, which mints them from `accounts.refresh_token` — the token in `accounts.access_token` is never refreshed after sign-in and is not to be trusted. Anything running tools must be on the Node runtime; `AsyncLocalStorage` does not exist on Edge.

**A refresh token is not forever, and every surface used to report the symptom instead of the cause.** Google ends one when the user revokes access, when they change their password, and — the case that actually bites — after **seven days** for any OAuth client still in "Testing" publishing status. So a deployment works perfectly and loses its calendar a week later, while the session goes on being valid for weeks: signing in is not the same as having Google access, and "увійдіть у застосунок ще раз" was advice that could not be followed, because a live session makes `/signin` bounce straight to the dashboard. What the user saw was a briefing saying the calendar could not be read, a bot saying "щось пішло не так на моєму боці", and nowhere at all the words "grant access again". `lib/auth/google-access.ts` is the shared vocabulary that fixes it: `classifyGoogleTokenFailure` reads a failed refresh as either `expired` (Google's `invalid_grant` — the permission is gone) or `unavailable` (a timeout, a 5xx, or an `invalid_client` that means *this deployment's* credentials are wrong), and only `needsReconnect` cases are ever put to the user. That is the `images:prune` rule again — only an explicit refusal counts as gone — and it is load-bearing in a new way here: a message that means "act now" is spent every time it goes out over an outage the user cannot affect, and after two of those it is not read at all. Both token modules classify through it (`lib/auth/google-token.ts` for web and Telegram, `lib/push/google-token.ts` for cron, whose `getAccessTokenResult` exists so the briefing learns the reason without a second round-trip).

The repair is one flow with three doors. `/google` in the bot checks live and answers one of three ways — alive, ended (with the numbered steps and the link), or Google not answering (wait, and here is the link anyway) — and it is a command rather than something the agent handles, on the `/unlink` precedent: it is asked exactly when the assistant is half-broken, so an answer that depends on the model working is an answer that may not come. Settings → Google (`app/settings/GoogleAccessPanel.tsx`, `GET /api/google/status`) holds the button itself, which calls `signIn('google')` outright rather than linking to `/signin` — the provider already sets `prompt: 'consent'`, so this always returns a fresh refresh token, which `persistGoogleAccount` writes to the account row that cron and Telegram read. And the morning briefing carries the news, because it arrives whether or not anyone opens the app, which is precisely how a dead permission went unnoticed for five days: `CalendarProblem` splits the `events === null` case in two, so `copy.briefing.googleAccessExpired` names `/google` and the plain `calendarUnreadable` no longer guesses at a cause it cannot see. The status is always checked by minting a token rather than by reading `accounts.expires_at`, since that column is only as fresh as the last background job and a status panel that can be confidently wrong is worse than none.

Two supporting fixes were needed, both of them the same bug one layer down. `getCalendarUserOrThrow` throws a typed `GoogleAccessError` whose message is written *for the model* — the AI SDK feeds a failed tool call back into the conversation, so that text is what the assistant reads before answering, and it says in as many words never to report an empty day. And `refreshAccessToken` in `app/api/auth/auth.ts` now drops the access token on failure instead of spreading `...token` over it: keeping it meant every web caller saw "there is a token", handed Google an expired one, and got back a 401 that surfaced as "could not read your calendar" — the one phrasing that hides the only actionable fact. Nothing is lost by dropping it, since that branch is only reached once the token has expired anyway.

### Key Layers

- **Auth**: NextAuth v5 (beta) with Google OAuth, JWT strategy, automatic token refresh. Config in `app/api/auth/auth.ts`. Session includes `accessToken` for Google API calls. Google OAuth scopes include Calendar read/write. Who may hold an account is decided by `ALLOWED_EMAILS` in the `signIn` callback (`lib/auth/allowlist.ts`) — an unset list means open, deliberately, because failing closed on an empty value would lock the owner out on the deploy that introduced the check. Since sessions are JWTs and never re-checked against the database, removing an address only blocks the next sign-in; evicting a live session takes a `NEXTAUTH_SECRET` rotation.
- **Database**: PostgreSQL with Drizzle ORM. Schema files in `lib/db/schema/`. Requires pgvector extension for embeddings (1536-dimension vectors). Followed calendars stored as JSONB on the user record (`users.followed_calendars`).
- **Calendar Service**: `lib/services/calendar.ts` wraps the Google Calendar API. Used by both API routes and AI tools.

**Overlapping in time and being in the way are different questions.** `findOverlapsForTimeRange` (`lib/utils/calendar-conflicts.ts`) counted every returned event as busy, so an anniversary — an all-day event, therefore midnight to midnight — collided with every hour of the day it fell on, and a request for 14:30 came back as a clash with alternatives on the *following* evening, twice, because a birthday had taken every hour there was to offer. `nonBlockingReason` excuses four kinds: all-day, `transparency: 'transparent'` (Google's "Free" toggle, how a standing working-hours block is normally kept), `eventType: 'workingLocation'`, and an invitation the user declined — the last on the reasoning that put `isDeclined` in front of the briefing. It filters the `busy` list in `suggestAlternativeSlots` too, or the two contradict each other and a day has no conflict and still no free slot. What is excused rides back as `alsoDuring` rather than being dropped: the point is to stop vetoing, not to stop noticing. And a check the protected person cannot overrule is a lock — the failure result now names `ignoreConflicts=true` and the system prompt says a clash is a question asked once, since two explicit confirmations were ignored while nothing anywhere said what the flag was for. Separately the search for the event to move is ±72h, not ±24h: it is by definition not where it is wanted, and "no, today" about something on Tuesday found nothing and wrote a second copy. Not a week — a weekly series puts one instance inside three days and two inside seven, and a second candidate makes the move refuse outright.

**An hour belongs to whoever's day it is.** Three places asked `Date.getHours()` — the server's clock, UTC on Vercel — for a number that only means something in the user's zone. The night guard in `suggestAlternativeSlots` turned "nothing before 07:00, nothing after 22:00" into 10:00–01:00 for a Kyiv user; it now measures in the offset of the requested time (`isSlotWithinHours`, exported because that bug is visible or invisible depending on where the suite runs). The two callers know that offset differently, which is why fixing one was not enough: `scheduleEvent` arrives with a real offset — its schema rejects `Z` and `+00:00` so that it does — while `optimizeSchedule` works in `Date`s and can only pass `.toISOString()`, always parsed back as `+00:00`, so the guard reverted to UTC for the one caller whose job is rearranging a working day. It passes `timeZone`, which wins. Its own `withinWorkingHours` had the identical bug, enforcing `workDayStartHour`/`workDayEndHour` three hours behind its user; it asks ICU for the zone's wall clock rather than doing offset arithmetic, so DST days come out right too.

**A calendar is chosen from the account, not typed.** Following one used to mean entering its id, which made a calendar reachable only if the user already knew its address — so the two most useful on any personal account were effectively unreachable, Birthdays living at `addressbook#contacts@group.v.calendar.google.com`. It also took the id on trust, and `fetchEventsBetween` drops calendars it cannot read via `Promise.allSettled`: a typo was stored, produced nothing forever, and said so nowhere. `listCalendars()` asks Google what the account has and the settings panel is a list of switches; `getCalendar()` verifies the one case the list cannot cover — a shared calendar the user was sent but never subscribed to — and the stored `summary` is Google's own (`summaryOverride` first, since a rename in Google is the user's) rather than a label typed once and left to drift. `listCalendars` throws rather than returning `[]`, because to a picker "Google would not answer" and "you have no calendars" look identical and mean opposite things. `users.followed_calendars` keeps its `{calendarId, summary}` shape, so none of this needed a migration. The account's own calendar is never stored: Google answers for it both as `primary` and under the user's email, so following yourself by address had it fetched twice on every read — `calendarIdsFor` (`lib/utils/calendars.ts`, dependency-free so the client panel can import the types) drops it by matching the email, since the callers that need this run on cron paths with no session to spend a lookup on.
- **Environment**: Validated with `@t3-oss/env-nextjs` in `lib/env.mjs`. Set `SKIP_ENV_VALIDATION=1` to bypass validation (useful for build/CI).
- **UI**: Tailwind CSS + DaisyUI with custom themes (silk, bumblebee, autumn). UI primitives in `components/ui/`, app components in `app/components/`.

### Schema Overview

- `users` / `accounts` / `sessions` — NextAuth tables (UUID PKs)
- `resources` — user content with optional metadata (type, tags, facts, entities, key points)
- `entities` / `entity_mentions` — the graph over those notes; `entities.relationship_source` (`model` | `user`) says whether the relation beside the name is extraction's reading or the user's word, and is what stops the next mention overwriting a correction; `entity_aliases` — spellings the user has decided mean an existing node; `entity_exclusions` — names they have decided are not nodes at all, which is what makes a deleted entity stay deleted
- `embeddings` — vector embeddings with source enum (`resource` | `table`), HNSW index. Calendar events are **not** indexed: an early sync that copied them here is gone, and `getEvents` answers from the live API instead.
- `conversations` / `messages` — chat history per user
- `user_tables` / `user_tables_data` — user-created custom tables
- `quick_actions` — a saved row template with a button on it; `fields` is `{ columnId, kind: fixed|today|now|ask, value?, prompt? }[]`, the label is unique per user (it is what a Telegram reply is matched on), and `last_used_at` is what the button reads back as "вже сьогодні"
- `timeline_events` — one row per dated thing, `occurred_on` plus a `precision` saying how much of it is real and a `recurrence` saying whether it comes round; `resource_id` cascades from the note that is its evidence, `entity_id` sets null
- `tasks` — the things that have to be done. Two independent dates: `due_on` (the deadline, never written to Google) and `scheduled_for` (the day of work, which *is* the calendar event, tracked by `google_event_id`). Identity is unique only among open rows, so a task done and raised again is a new one
- `task_completions` — one row per closing, which is the only past a rolling recurrence has; `UNIQUE (task_id, completed_on)` is what makes a double button press safe
- `task_suggestions` — needs already accepted or dismissed. The suggestions themselves have no rows: they are computed from every note's `metadata.needs` minus this table, the mirror of `entity_exclusions`
- `wellbeing_entries` — one row per state check-in (mood/energy 1–5, `sleep_minutes`, symptoms, note), `local_date` denormalised for charting, `resource_id` pointing at the searchable copy of the note
- `assistant_directives` — standing response preferences, injected into every system prompt (capped at 20 × 200 chars, `source` = `user` | `inferred`)
- `users.telegram_chat_id` — where notifications are delivered; an account without one is unreachable
- `users.locale` — `uk` | `en`, the language notifications are written in (default `uk`)
- `notification_queue` — queued notifications (`pending` → `sending` → `sent`|`failed`), delivered via QStash callbacks or the cron sweep
- `sent_notifications` — dedupe ledger of already-delivered notifications
