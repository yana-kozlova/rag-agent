# Resources and notes

**`metadata.type` has one list, and the Knowledge Base filter is counted, not written.** The type enum lived in four hand-maintained copies — the zod schema, the extractor, the `/resources` filter dropdown and its edit form — and they drifted apart: the filter offered types nothing carried while omitting `image`, `event`, `preference` and `need`, so notes the extractor had been classifying for months were unreachable from the page whose job is to reach them, and re-saving a `preference` through the editor silently retyped it to `note`. `lib/utils/resource-types.ts` is now the only list (in `lib/utils` so a client component can import it without dragging drizzle into the browser — same reason as `lib/utils/uploadable.ts`); `EXTRACTABLE_RESOURCE_TYPES` is it minus `image`, which the vision path assigns from the fact that bytes arrived and no model may infer from prose. The filter's options come from `collectFacets` (`lib/utils/resource-facets.ts`) counting the user's own rows, shared by the page's first paint and `/api/resources/tags` so the two cannot disagree. An unrecognised type is kept and sorted last rather than dropped — `metadata` is `passthrough()`, and hiding a row is the original bug in a new costume — and an absent type counts as `note`, which is why the API filters on `coalesce(metadata->>'type', 'note')`.

**Images are stored as text.** A photo or screenshot is read once at the door by a vision model (`lib/ai/vision.ts`, `AI_VISION_MODEL`, defaults to the chat model) which names what it shows and transcribes any text on it verbatim; that description becomes the resource's `content`, so chunking, embedding, extraction and hybrid search all work unchanged and never learn about a second modality. The bytes go to Vercel Blob (`lib/storage/images.ts`, `BLOB_READ_WRITE_TOKEN`) and the URL is kept in `metadata.imageUrl`. Both halves degrade independently and on purpose: a failed description aborts the upload (an unsearchable image is invisible to the assistant), while a failed store only logs and the resource is saved without a URL. `lib/actions/save-image.ts` owns that ordering so no surface re-decides it. Note that Vercel Blob has no private tier — every object is served publicly and the unguessable URL is the only protection, so nothing harmful-if-leaked belongs here. A store that is deleted and recreated gets a new id, which orphans every URL already saved against the old one: the row still claims a picture, and the Knowledge Base card renders an empty box where the description preview would have been. `pnpm images:prune [--dry]` drops `imageUrl`/`imagePathname` from those rows and nothing else — the description is still true and still searchable, and a resource without a URL is the state an upload with no `BLOB_READ_WRITE_TOKEN` already produces. Only an explicit 404 or 410 counts as gone; a timeout or a 5xx means "could not tell", and erasing a live URL on that evidence is the one mistake here nothing can undo. Client-side pickers validate against `lib/utils/uploadable.ts`, which is dependency-free precisely so a client component never pulls `unpdf`/`mammoth`/the AI SDK into the browser bundle.

**An EPUB is read in spine order.** An EPUB is a ZIP of XHTML read in the order the package document's *spine* gives, not filename order — concatenating the files alphabetically scrambles the book and makes retrieved passages read as if they came from the wrong chapter. Extraction lives in `lib/utils/epub.ts` (no XML parser: the two files that need reading have a flat shape and the rest is being reduced to text anyway); DRM-protected books are detected via `META-INF/encryption.xml` and refused, because their XHTML unzips fine and decodes to noise.

**A note is a dossier, not a transcript of one message.** `addResource` used to insert unconditionally, so one message about Andriy produced two notes 900 ms apart and the graph split the owner's identity three ways behind them. It now routes: `findDossier` (`lib/actions/note-routing.ts`) looks for an existing note *about the same subject*, and `updateResource` folds the new fact into it. The routing is deterministic on purpose — a note qualifies only when the incoming content has exactly one graph-worthy entity, is under `MAX_ROUTABLE_LENGTH`, and the target note has that entity as its **sole** subject. The alternative, asking an embedding whether two texts are "the same", needs a threshold thin enough to separate "Андрій is my husband" from "Андрій was born in 1985" — two different facts about one person, sitting very close together. Routing by subject removes that razor; a big import therefore always becomes a new note rather than being smeared over everyone it mentions.

**A note is stored once, not five times.** `formatStructuredContent` (`lib/ai/information-extraction.ts`) writes the summary and the key points — nothing else. It used to append the facts, the entities and the needs as prose too, so one request for a pediatrician's certificate was stored as a paragraph, the same thing as bullets, again as subject-predicate-object, again as "name - type (relationship)", and once more as a need: 190 characters of information kept as 743. All three are already in `metadata` in the machine-readable form the graph and the merge check read, and prose copies of them were never the source of anything. The second-order costs were the expensive part — retrieval scored five near-identical chunks where one claim existed, and the inflated length was measured against `MAX_ROUTABLE_LENGTH`, so a one-line fact about Артем cleared 600 characters, was declined as an import, and became the second note about a person who already had one. That is the exact duplication the routing exists to prevent, caused by the routing's own preprocessing; `addResource` now measures what the user typed. `keyPoints` stays in the text because the embedding is built from it and that is where the dates and names are. `pnpm kb:compact [--dry]` takes the old restatements back out of notes already saved and re-embeds them, removing a line only when regenerating it from that note's own metadata reproduces it character for character — so text since merged, rewritten or hand-edited is left alone.

**A rewrite is never trusted to keep what it was given.** `mergeNoteContent` (`lib/ai/note-merge.ts`) asks the model for a merged note, then checks every fact from the old note's `metadata.facts` still has its subject and object present — predicates are allowed to be rephrased, anchors are not allowed to vanish. A rewrite that drops one, or that collapses below `MIN_LENGTH_RATIO` of the original, is discarded and the new material is appended instead. Worse prose, zero silent loss. The anchors are matched word by word, minus stopwords and minus a long token's last character. Matching each anchor as one string only ever worked because the note being checked *contained the fact list verbatim* — once the restatements above were gone the same fact had to be recognised in the summary carrying it, where it reads "a medical certificate from a pediatrician for her child, Artem" and no contiguous run matches. A check that strict would reject every rewrite and silently turn merging back into appending, which is how a note starts repeating itself again; the trailing character goes because the merge prompt answers in the note's language and Ukrainian inflects "Андрій" to "Андрія", where neither string contains the other.

**A note is written in the language the user typed it in.** Nothing ever said "write in English", but the extraction prompt's only worked example took a Ukrainian message and returned English facts, entities and a summary — a demonstrated translation is a stronger instruction than any sentence, so a Ukrainian base was stored in English. The cost is not aesthetic: `addResource` keeps only the extractor's output as the note's `content`, so the words the user typed survive nowhere, the lexical retriever holds English tokens while the question arrives in Ukrainian, and `entities[].name` becomes whatever the model transliterated this time. Identity is `(user_id, normalized_name, type)` and `normalizeName` only lowercases, so "андрій" and "andriy" are two rows — and `findDossier` matches that same key exactly, so a spelling that drifted between two saves fails to find the dossier and writes a second note about a person who already has one. That is the duplication note routing exists to prevent, caused upstream of it. The rule is therefore the source language, not a setting: forcing a chosen language would translate a pasted English article out of its own vocabulary, and applying it to names would make the graph split *toggleable*, which is worse than a split that is at least deterministic. Four fields stay English whatever the message says — `contentType`, each entity's `type`, each need's `priority` and every tag — because they are matched against code: `GRAPH_TYPES` is an English set, and an entity typed "особа" is silently never made a node. Two worked examples now carry the rule in both directions, since one Ukrainian example alone would just reverse the bias.

A fact about the account holder is extracted with a *placeholder* subject — the word for "user" in the message's language, never their name — and those words are in `note-merge`'s `STOPWORDS`. The subject of such a fact is a word the note itself has no reason to contain: it names the person or speaks in the first person. Anchoring on it passed only while notes were English and the summary happened to open "User requests…"; in Ukrainian every fact about the user would read as dropped, rejecting every rewrite and turning merging back into appending with nothing in the log. The object is what carries the claim, and it is still checked.

**Books are the reason embedding is batched.** A book chunks into the high hundreds, past OpenAI's per-request ceiling of 2048 inputs / 300k tokens, so `generateEmbeddings` splits into sequential batches — one request per book would fail on exactly the uploads this was built for. For the same reason `extractStructuredInformation` reads only the first 60k characters: a whole book exceeds any chat model's context, and an over-long prompt fails both attempts and leaves the book with no tags, facts or entities at all.
