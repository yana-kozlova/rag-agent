# Tasks

**A deadline and a day of work are different dates, and keeping only one of them is wrong in one of two ways.** Keep only the deadline and every task shouts on the day it is due and is silent for the fortnight when it could actually have been done; keep only the working day and nothing knows Friday is the last chance. So `due_on` is the last acceptable day and never leaves this app, while `scheduled_for` is the day the user committed to doing it — and committing is what writes a Google Calendar event, because at that point it really is a plan for a day and belongs beside everything else claiming that day. That boundary is the whole design: the calendar stays a record of days the user agreed to spend rather than a pile of everything outstanding. A task carrying neither date is not broken, it is the ordinary "sometime" item that a list of only dated things has nowhere to put — and the page shows all four groups at once rather than only today, because a deadline a fortnight out is exactly what you want to see while there is still a choice of days to do it on.

**This layer was designed into the app before it existed.** `metadata.needs` has been extracted from every note for months with **zero** read consumers, and `DATE_EXTRACTION_RULES` refuses deadlines from the timeline in as many words — "a deadline is a *task*… `needs` already carries it in metadata waiting for a tasks layer to read. Putting it on the axis makes the axis a worse to-do list." So deadlines landed nowhere at all: not the timeline (refused), not the calendar (not an event), not tasks (absent). `listTaskSuggestions` is the consumer, and it computes rather than stores — a suggestion is a *reading* of a note, and materialising readings means keeping them in step with notes that get edited, merged and compacted. `task_suggestions` records only decisions, accept and dismiss alike, since both mean "handled" and only provenance differs. Nothing lands automatically: extraction is liberal by the same design that puts a greeting in the entity graph, so "хочу колись вивчити React" arrives looking exactly like "подати заяву до 17.08".

**All-day and timed are two different promises, and Google is told which.** A day with no hour becomes an all-day event marked `transparency: 'transparent'` — it holds no time, so it must not veto a meeting and must not appear in the briefing's schedule beside its own line in the tasks block. A day with an hour is an ordinary opaque event. Note the asymmetry that makes the Free flag necessary at all: `nonBlockingReason` already returns `'all-day'` before it looks at transparency, so conflicts were never the problem — `fetchEventsBetween` was, since it filters on `isTimeBlock`. Three fixes had to land in `lib/services/calendar.ts` first, because the wrapper could express none of this: `createEvent` hardcoded `{ dateTime }` so all-day was unreachable; `patchEvent` did too, so an event could never be converted between the two without a delete-and-recreate that changes the id the task row holds (it now sends the unused field as an explicit `null`, which is how Google is told "and not that one"); and `deleteEvent` re-threw on 404/410, so a user who removed the event on Google's side could never unschedule the task pointing at it — every attempt failed and the row kept a dead id forever. Writes go to `'primary'` and never through `scheduleEventTool`, whose `moveIfExists` would fuzzy-match two similarly-named tasks within ±72h into one, and which needs a session the cron path does not have.

**Rolling a recurrence forward is anchored to the schedule and always lands past today.** Miss three days of vitamins and the next dose is tomorrow, not the day before yesterday: a recurrence that re-emerges already overdue can never be caught up with, and a list that permanently accuses is a list that gets ignored. `nextDueDate` always recomputes from the *original* due date rather than stepping from its last answer, or one February turns a "31st of the month" task into a 28th-of-the-month task permanently. History comes from `task_completions`, one row per closing — a single rolling row otherwise has no past, and "чи приймала я вітаміни цього тижня" has no answer. Its `UNIQUE (task_id, completed_on)` is not tidiness: Telegram's `clearReplyMarkup` is best-effort, so the same button really can fire twice, and rolling twice would silently skip an occurrence. What is deliberately **not** expressed is "every two weeks from whenever I last did it" — a real and different intention, one field and one migration away.

**Identity is open-only, and fails open.** `tasks_open_identity_unique` is `(user_id, lower(btrim(title)), coalesce(due_on, DATE '1970-01-01')) WHERE status = 'open'` — partial *and* expression, so drizzle can express neither and it lives only in migration 0027 (never `db:push` this table, same hazard as `timeline_events`). Partial because a task done in March and raised again in August is a new one, and refusing it would be indistinguishable from the save silently failing. `coalesce` because Postgres treats NULLs as distinct and two undated "подзвонити в садок" would otherwise both insert. It catches case and outer whitespace and deliberately not internal whitespace or word order — a visible duplicate can be deleted, a silently swallowed task cannot be recovered because nobody knows it was ever asked for. Drizzle only permits the bare `onConflictDoNothing()` here (an explicit target is built from column names and cannot name an expression), so the read-back after a rejection must match all four parts of the index by hand, the status predicate included, or the model is handed a completed task and told "already have it".

**Closing is a tool, deleting is a route.** The wellbeing and timeline line, drawn for the same reason: closing is reversible — the row stays, `reopenTask` puts it back, the completion log keeps its record — and deleting is not. An ambiguous name is reported back rather than resolved, on the `matchDirective` precedent and for a sharper version of its reason: closing the wrong task removes something that still needs doing from the only list tracking it, and the user finds out when the deadline has passed.

**Overdue tasks are asked about one message at a time.** Buttons under the briefing itself do not survive contact with the code: `clearReplyMarkup` wipes a keyboard entirely and does so deliberately, so that "Save" on a week-old briefing cannot file a second copy — pressing one task's button would retire every other task's too — and `snooze` rebuilds the notification from its text with a hardcoded action list, so the lines would come back with no buttons under them. One short message per overdue task sidesteps all of it: each carries its own keyboard, a press clears only its own, and none of the notification machinery changes. `t:` is the fourth callback namespace beside `n:`, `q:` and `qu:`, and the task id rides in `callback_data` rather than being read back off the message text — which is exactly what lets a press identify its own task. "Tomorrow" moves the *deadline*, since that is what makes the task overdue; nothing moves a date without a press. Fixing this also closed a latent bug: `handleCallbackQuery`'s `runWithUser` never supplied `resolveAccessToken`, so any button touching Google would have thrown `Unauthorized`.

**The briefing block is assembled, and survives an unreadable calendar.** `taskLines` prints lateness the application computed — the rule this file already follows for `scheduleLines` and `dateLines`, and it matters more here, since a briefing claiming a deadline passed two days ago when it passed five is worse than one saying nothing. Tasks come from our own table rather than from Google, so they go out under `calendarUnreadable` for the same reason saved dates do.

A task committed to today is normally absent from the block, because committing writes a calendar event and it is therefore already in the schedule above — printing it again would show one commitment twice under two headings. *Normally*: `outstandingTasksForBriefing` takes `inSchedule` because that reasoning assumes there is a schedule for the task to be in, and twice there is not. When the calendar could not be read at all, and when the row carries no `google_event_id` because writing the event failed, the day's committed work was printed **nowhere** — dropped from the tasks block as a duplicate of a list that did not exist. That is this block's own reason for existing, failing one step in: tasks live in our own table precisely so a broken calendar cannot swallow them, and then a broken calendar swallowed them anyway. It was invisible for as long as it was because it needs the calendar to be down to appear, which is exactly when nobody is auditing the tasks block.

**Two piles are counted, never listed.** `BriefingCounts` carries the undated tasks (`buckets.someday` — open, no deadline, no day of work) and the undecided needs sitting in notes (`listTaskSuggestions`, which until now nothing read outside `/tasks`). Neither moves day to day, so lines would be wallpaper inside a week while a count still says whether the pile is growing. The needs count is deliberately a number and not the titles: *that many undecided readings exist* is a fact, but which of them is really a task is a model's guess, liberal by the same design that puts a greeting in the entity graph — and every other line in this briefing is assembled from facts, so printing "подати заяву до 17.08" beside "хочу колись вивчити React" would put a guess in among them wearing the same clothes. It is its own block rather than a tail of the task list because it is not the task list, which is also what lets it go out on a morning when nothing is due; the undated count *is* a tail, under the same header, because those are tasks. Both are read through the same `listTaskSuggestions` default the page uses, since a briefing quoting a count the page then contradicts is worse than no count.
