# Entity graph

**Entity identity is resolved by the user, made permanent by aliases.** `lib/actions/entity-identity.ts` folds names (Cyrillic → Latin, `y`/`j`/`i` collapsed, repeats squashed) so "Андрій"/"Andriy" and "Yana"/"Yana Kozlova" can be *suggested* as one person — deliberately over-eager, because a declined suggestion costs a click and a missed one splits the graph forever. Nothing merges automatically: `findMergeCandidates` proposes, the user confirms in `app/entities`, `mergeEntities` repoints mentions and drops the loser. Merging alone would not survive, since identity is `(user_id, normalized_name, type)` and the next note would recreate the node — so a merge writes an `entity_aliases` row, and `syncEntitiesForResource` consults it before creating anything. Two exceptions: the account holder is collapsed automatically (`resolveSelfName`) because the signed-in name is known and it is not a judgement call, and a shared surname is never offered as a match.

**Renaming a node and merging two are the same operation, and both are alias writes.** The suggestion rules are narrow by construction, so the pairs they cannot propose — a bare surname against a full name ("Коваленко" is not a prefix of "Андрій Коваленко"), a diminutive, an abbreviation, a name filed under two types — need a hand, and the correction is one question: *this is actually…*. `EntityIdentity` on `/entities/[id]` asks it once; a name that already belongs to a node becomes `mergeEntities`, and a name that belongs to nothing becomes `renameEntity` (`lib/actions/entity-rename.ts`). Editing `entities.name` alone would be pointless — the column is "as last written by the model" and `syncEntitiesForResource` rewrites it on the next mention — so a rename writes two `entity_aliases` rows, the old spelling so notes still using it land here instead of recreating the node, and the new one so nothing overwrites the name the user just chose. That is also why the alias path in `syncEntitiesForResource` still fills in `relationship`: skipping the upsert must cost the spelling, not everything later notes learn. `planRename` separates a *respell* (same normalized name, so it cannot collide) from a *rename* (a new identity, so an occupied one is reported back as the merge that was meant). Merging across types is allowed here though never suggested — nothing in the transaction depends on types matching, the winner's survives, the alias keeps the loser's, and the model files one project as `project` and `organization` often enough that this is the ordinary manual case. Manual merge stays as irreversible as the suggested kind, which is why the confirmation spells out what moves and which name disappears, and why direction is switchable rather than decided by `pickWinner`.

**Deleting a node is a standing rule, not a row — and it is the one entity action that can be undone.** Rename and merge both assume the node names something; neither answers the third way the graph goes wrong, which is a node made of what was never a subject — a greeting read as a person, a stray noun read as a place, the liberality of extraction showing through. A bare delete would not survive: `entities` is the projection of every note's `metadata.entities`, so the next mention upserts it straight back, and it returns with a mention count of one while twenty notes still talk about it, which reads as data loss rather than as a delete that failed. So `deleteEntity` (`lib/actions/entity-delete.ts`) writes `entity_exclusions`, the mirror of `entity_aliases` — an alias says a spelling means *that* node, an exclusion says it means nothing, and `syncEntitiesForResource` consults both before the upsert. Keyed on the same triple as `entities.identity`, so burying the project called Sequoia says nothing about the place; the node's own aliases are buried alongside it, or a node that had absorbed three spellings rebuilds itself under one of the other two. Nothing the user wrote is touched — the notes keep their words and their `metadata.entities`, retrieval still finds them, `timeline_events.entity_id` sets null rather than cascading — and that is precisely what lets `restoreEntity` rebuild the node rather than only lift the tombstone: the evidence is still there, so the sync is replayed over the notes that still name it, capped by `MAX_REBUILD` because a two-letter name matches a lot of prose. A merge or a rename calls `clearExclusions` on the spellings it claims, since the later decision wins and a tombstone standing over a live node would list a name as hidden while its page is open. The buried names are shown on `/entities` rather than nowhere: a delete that quietly filters every future save is indistinguishable from a bug unless it can be read back and lifted.

**A relationship is to the user, and the user gets the last word on it.** Merge, rename and delete all repair a node's *identity*. The fourth thing that goes wrong leaves the identity correct and the one editorial line wrong: `entities.relationship` means "how this node relates to **the user**", and extraction fills it with whatever relation the sentence happened to state. "Артем — похресник моєї куми" is a true sentence about the godmother, and it is stored as *the user's* godson — so a son is labelled a godson on his own page, in the entity list, on the people widget and in the note view, in each case printed beside the name as fact rather than as evidence. The prompt now says the field is to the user and nobody else, and that a third-party relation is either written out in full ("godson of the user's kuma") or left null; the schema's `describe` says it too, since that is what the model actually reads. But a prompt is a tendency, so `setRelationship` (`lib/actions/entity-relationship.ts`) is the correction — and it has to be a decision rather than an edit for the same reason a rename does, because `syncEntitiesForResource` rewrites this column from every note that mentions the node and a plain edit would revert at the next mention with nobody watching. `entities.relationship_source` (`model` | `user`) is what the sync consults, in both branches: the alias path updates only where the source is still `model`, and the upsert's `coalesce` sits inside a `case` on it. One flag on the row rather than a table like `entity_aliases`, because unlike a name this value rides on a row the sync updates in place and never recreates. Blank is an answer and not an absence — "they are nothing in particular to me" is exactly the correction a wrongly-lifted relation needs, so the source is what a merge keys on and `pickRelationship` gives a hand-set value the win from either side (which of two duplicates survives is decided by mention count, something the user never sees and never chose). `resetRelationship` hands the field back to extraction and leaves the current wording standing, since the notes are untouched and the next mention fills it in again; that undo is possible for the same reason `restoreEntity`'s is. The one thing it does not survive is a delete, which drops the row — a restored node comes back with the model's reading.
