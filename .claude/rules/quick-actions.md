# Quick actions

**A routine is a button, not a sentence said again tomorrow.** Both existing ways to write a table row go through the model — `addTableRows` reads a sentence, `extractToTable` reads a note — which is right for a fact stated once and wrong for a thing done daily: "Арчі прийняв ліки" cost a chat completion, a tool round-trip and several seconds to store six characters that never vary. A quick action (`quick_actions`, `lib/quick-actions/quick-actions.ts`, `lib/actions/quick-actions.ts`) is that row minus what the model was being asked to infer — invariant columns stored as literals, the date stamped at press time, and only what genuinely changes asked for. Pressing it calls no model: `POST /api/quick-actions/[id]/run` is session → resolve → insert, and the only remaining API cost is the embedding, which stays because a row nothing can find is not saved in any sense this app means and is three orders of magnitude cheaper than the completion it replaces. What it is deliberately **not** is a schedule — nothing knows the medicine is daily, nothing nags, nothing back-fills a missed day. The routines here are not predetermined ("today Арчі, tomorrow me, the day after a child's temperature"), and a button that assumes otherwise starts lying the first week it is wrong.

**A button that asks is a button that has failed.** The first thing the assistant did with this feature was create "Арчі — ліки" with three `ask` fields — which medicine, what dose, any notes — for a row whose every column is the same six characters every day. That is the add-row form with an extra tap in front, and it re-introduces the exact cost the feature exists to remove: the user is typing again, and a press that was supposed to be free now waits on them. The mistake is structural rather than careless — a model that has not been *told* a value reaches for `ask`, because asking is how it obtains anything — so the fix is stated in three places and enforced in one. The prompt and the tool description say the target is zero questions, that the values come from what the user just said or from the row just written into that table (that row **is** the template), and that a missing value is a reason to ask *in the conversation, once* and store the answer as a literal. `asksMoreThanItKnows` then refuses to save a button that asks for more of the row than it fills — a ratio rather than a count, since one question on a two-column table is a reading with its date stamped while three on a five-column table is a form. Its rejection message spells out the repair, because the cap that already existed (`MAX_ASK_FIELDS`) taught nothing: told "at most 3", the model simply asked for 3.

**The repetition is in the table, so nothing has to notice it.** The deeper fault was upstream of any of that: a button existed only when someone thought to ask for one, and the prompt's answer was to tell the model to spot the pattern itself — "two or three near-identical rows into the same table is the signal". That instruction could only ever fire inside a conversation that happened to contain the rows, which is the one place the evidence is *not*: the user writes the same row every day, each time in a fresh chat, and the fortnight of identical rows sits in the table where nobody looks. `detectRepeatingRow` (`lib/quick-actions/detect.ts`) looks. It groups the recent rows on the columns that do not vary, and a group of three on three different days is a routine: the repeating values become `fixed`, a date column that tracks the day the row was written becomes `today`, and a column that differs every time *and is usually filled* becomes the one `ask` — which is `MAX_SUGGESTED_ASKS`, stricter than the guard above, because an offer nobody asked for has to be a button worth pressing without reading it. `addTableRows` runs it after writing and hands the template back in its own result, so the offer arrives at the moment the user has just done the thing by hand again; the model passes those fields through rather than re-deriving them, and the prompt bullet telling it to count rows by eye is deleted rather than left standing beside a mechanism that does it properly.

**And once the table notices, the model must stop noticing too.** Leaving `createQuickAction` described as "call it when a record repeats" beside a detector that reads the rows meant both fired at once: one conversation about Арчі's pills produced a model-made button — evening dose, and asking for the *date*, which is the one value the clock already knows — while the table page offered the morning dose it could see in seven rows across seven days. Two standing objects on the user's screen where none had been asked for, and the worse of the two was the one the model volunteered, because it was inferring a template from a conversation while the other read it off the data. The prompt and the tool description now name two triggers and no others — the user asks in so many words, or `addTableRows` said NOTICED and they said yes. The tool is kept rather than deleted: "зроби кнопку" has to work on the day someone says it, and the detector cannot answer for three days.

A routine already covered is now told to the detector rather than filtered out of its answer, which is what makes offering the *second* routine in a table possible at all. `detectRepeatingRow` returned the biggest group and the caller dropped it when a button matched — but the biggest group is the biggest group tomorrow as well, so accepting one offer silenced the page permanently, with the evening dose still being typed by hand every night. It now walks the groups in size order and answers with the first that no button covers.

Three details are load-bearing. Days are counted from the row's own date column when there is one, not from `created_at` — "я всі ці дні давала Арчі ліки, заповни таблицю" writes a fortnight in one afternoon, and counting when the rows were *written* would read that as a single event and decline to notice the very routine being described. A date column only becomes a stamp when the rows show it tracking either the day they were written or a different day each time; otherwise an expiry date would be silently overwritten with today's on every press. And `covers` is one function shared by the detector and its two callers, so "this routine already has a button" cannot be answered two ways — comparing labels would not survive the user renaming one.

**An offer is a reading, and a reading gets one chance to be corrected.** Two things about the offer were wrong in the same way: it presented what the rows say as though it were already a decision. The face was `values.join(' — ')` cut at `MAX_LABEL_LENGTH`, which turned a dog's daily dose into `Create "вранці — апоквель — у відповідності з пр"` — the third value is a notes column holding the same standing instruction every day, which identifies nothing and is exactly what pushed the name past its width, and a `slice` finished it mid-word. `labelFor` therefore builds the name from the values that read as *names* (`NAME_LENGTH`, three at most) and drops what does not fit whole rather than cutting it, falling back to a word-boundary clip with an ellipsis only when there is nothing shorter to use. And `RoutineOffer` now opens: the label and every `fixed` value are editable in place before the button is accepted, with the date stamp and the questions shown read-only because what they hold is decided at press time. A value cleared drops its column from the template rather than writing a blank on every press — an empty cell reads as "recorded, and there was nothing" — and a template with nothing fixed left cannot be created at all, which is `asksMoreThanItKnows` said in the client's own terms.

Editing is what forced `signatureOf` out. Identity by exact fields answered "does a button already cover this?" only while the button was the template verbatim; a user who drops the notes column or shortens a value creates a button that no longer matches the rows it came from, and the page goes back to offering a routine that has had a button on it since Tuesday — daily, until the old rows age out of `MAX_ROWS_SCANNED`. `covers` asks the question the accepting was an answer to: every field the button *writes* matches the routine's, and the columns it leaves out are the ones the user chose not to keep. Fixed values match on case, spacing and containment past `MIN_CONTAINED_LENGTH`, so "ліки" reworded as "ліки (апоквель)" is the same routine while "вранці" and "ввечері" remain two. A button carrying no fixed value of its own covers nothing, since a date stamp and a question describe every routine in the table equally well.

`kind` is `fixed` | `today` | `now` | `ask`. The two date kinds are separate rather than read off the column's type, on the timeline's `precision` reasoning: how much of a date is meant is a decision, not something to infer — a medication log wants the day, a temperature reading is worthless without the hour. `today` writes a bare `YYYY-MM-DD` and `coerceValue` now leaves such a string alone, because parsing it through `Date` makes it UTC midnight and prints as the day before west of Greenwich. Both are computed in `timezoneFor(userId)`, never the server's clock: at 01:30 in Kyiv the server is still on yesterday, and a dose filed a day early is never noticed. An unanswered `ask` **stops the write** rather than storing a blank — an empty column reads as "measured and found nothing", and no later view can tell the two apart. A field naming a column the table no longer has is skipped instead of written under a dead key, since columns can be renamed and deleted from the editor while a button still points at them.

**Undo, not confirm.** The button's whole value is that one tap ends it, and a confirmation doubles the interaction on the ninety-nine presses that were right to save a click on the one that was not — so the write happens and an undo stands for a few seconds (web toast, Telegram inline button). It deletes only a row *this* button wrote, checked against `metadata.quickActionId`, so a guessed row id cannot be laundered through it; and the usage stamp is then recomputed from the rows that remain rather than decremented, because decrementing gets `lastUsedAt` wrong — undoing this morning's press should leave the button showing yesterday's, and only the rows know when that was. `lastUsedAt` exists to answer the question a person actually has in front of a daily button (*did I already give him the pill?*), which is why it is read back onto the button face and not kept for analytics.

**The label is the identity, on both surfaces.** `UNIQUE (user_id, lower(btrim(label)))` stops the assistant creating a second "Арчі — ліки" it cannot tell from the first, and it is what makes the Telegram flow possible at all: a callback press carries no conversation, so a button that asks for a value sends a `force_reply` prompt with its label in guillemets and the reply is matched back on that. Hence `sanitizeLabel` — `sendMessage` strips Markdown on the way out, so a label written "Арчі *ліки*" would arrive as something else and match nothing; sanitising once on write is what makes the round-trip safe by construction rather than by every reader remembering to normalise. Several values are asked for in one comma-separated reply (`splitAnswers`), with the last field keeping any trailing commas because it is usually the free-text note; with one question there is no split at all. `MAX_ASK_FIELDS` is 3 — past that, pressing a button is not faster than the table's own add-row form. Callback data uses two more namespaces beside the notification `n:` one, and the parsers are mutually exclusive by test: a notification's "save" read as a quick action would write a row.

`MAX_QUICK_ACTIONS` (12) is the same reasoning as `MAX_DIRECTIVES` — past a dozen this stops being a row of buttons pressed without reading and becomes a list to search, at which point typing the sentence was faster. Hitting the cap is reported, never resolved by evicting the oldest. Buttons render in creation order rather than most-recently-used, deliberately: one pressed every morning should be in the same place every morning, and a list that reshuffles under a thumb is how the wrong row gets written. Deleting a button touches nothing it wrote — the rows are the record — and needs no tombstone, unlike `entity_exclusions`, because nothing recreates a quick action behind the user's back. Managing them lives on `/tables/[id]` and not on the dashboard, where a delete control beside a daily button is a mis-tap waiting to happen.

The column type list moved to `lib/utils/table-columns.ts` as part of this: it had two hand-maintained copies (`tableColumnSchema`'s `z.enum` and `create-table`'s `COLUMN_TYPES`), which is the exact drift `metadata.type` already went through, and the quick-action bar is a client component that needs the list and the coercion without dragging drizzle into the browser — same reason as `lib/utils/uploadable.ts`.
