# Calendar

**`getEvents` was the path all three calendar rules had been fixed around.** It is the tool behind every schedule question in chat and Telegram, and it had none of them. Declined invitations were listed. Nothing de-duplicated, so an event on both the user's calendar and a shared one appeared twice — and that ordering matters for more than tidiness: filtering declined per calendar would drop the user's own copy, the only one carrying their `responseStatus`, and keep the shared calendar's status-free twin, so the de-duplication is what makes the filter correct. A rejected calendar contributed nothing, logged nothing and threw nothing even when *every* calendar failed, which is the same "most confident possible way to be wrong" that cost the briefing five mornings; `CalendarUnreadableError` is thrown in that case and passed through the outer catch unchanged, because collapsing it into the generic tool failure is precisely how an unreadable calendar becomes indistinguishable from an empty one. The hand-built `['primary', ...followed]` list is gone in favour of `getCalendarIdsForUser`, which drops a followed calendar that is the user's own address — Google answers for it under both names, so following yourself fetched every event twice.

**Free time is not tracked, and the reason is not that it was hard.** `lib/utils/free-time.ts` computed a `[Free]` line per day — each open window, its length, the day's total — and `eventsToModelOutput` appended those lines to every `getEvents` result. Two things were wrong with it. The first is that nobody asked: the lines rode along under every "що в мене сьогодні", so a plain schedule question came back with a free-time total appended, which is commentary on someone's day rather than an answer. The second is that the number was wrong. `occupies` excused a block marked Free by calling `isTimeBlock(e)`, which reads `transparency`/`eventType` — and `get-events.ts` flattens those into a single `timeBlock` boolean at the door and carries neither field onto `ToolCalendarEvent`. So the check was structurally always false, a standing "Робочі години 08:30–18:00" was counted as busy, and a day with two evening events reported 2 год 30 хв free. It typechecked in silence because every field `FreeTimeEvent` wanted beyond `allDay` is optional, and the unit test passed because it built its fixtures with `transparency: 'transparent'` — the shape this path never produces. `attendees` was dropped the same way, so the declined-invitation exemption was dead too. The module, its test and the prompt rule telling the model to read the lines off are all gone; the system prompt now says free time is not tracked and that nothing may be derived from the times in a result, because deleting the tool line without saying so is an invitation to subtract the events in the reply, and that answer has no test behind it at all.

**The weekday is computed, never derived.** `getEvents` handed the model a bare ISO timestamp per event, so naming the day it fell on was arithmetic left to the model — and asked what was on this week it answered "18 серпня (четвер)" for a Tuesday and shifted every day after it. `weekdayOf` (`lib/ai/tools/events/get-events-format.ts`) puts `Day: Tuesday` in the line, on the rule the briefing already follows: anything derived from a date is the application's job, because a model asked to restate one eventually restates it wrong, and a schedule naming the wrong day is worse than one naming none. It reads the first ten characters rather than parsing through `Date`, since that prefix is already local to the event's own offset while `Date` answers in the server's zone. The same line now carries `Note: marked Free` for a `timeBlock`, which is the chat-side half of the entry below — the push path drops those events, but "що в мене цього тижня?" is a question about the calendar, so here the block is labelled rather than hidden, and the frozen byte-identical line test was updated on purpose rather than worked around.

**A block is not a commitment.** `isTimeBlock` (`lib/utils/calendars.ts`, which imports nothing, so both the raw Google shape and the normalized one can pass) reads Google's own answer: `transparency: 'transparent'` — the "Free" toggle — or `eventType: 'workingLocation'`. The writing path learned this first and the notification path did not, so a standing "Working hours 08:30-18:00" was counted as a commitment: listed among the day's tasks, inflating the count in `thingsToday`, and reported by `findConflicts` as a clash against every meeting inside it — three overlap alerts in one morning, each telling the user that working during working hours is a problem. It is filtered in `fetchEventsBetween` beside `isDeclined`, and both now live in this file for the reason written there: a rule that has to be remembered by three callers gets remembered by two. `schedulable` keeps its own guard anyway, since `scanDay` takes its events as an argument. Focus time and out-of-office are deliberately not excused — they hold the time, and only the Free flag says otherwise. Note the limit: a working-hours block that is *not* marked Free is indistinguishable from a meeting, and nothing here matches on a title.

**Overlapping in time and being in the way are different questions.** `findOverlapsForTimeRange` (`lib/utils/calendar-conflicts.ts`) counted every returned event as busy, so an anniversary — an all-day event, therefore midnight to midnight — collided with every hour of the day it fell on, and a request for 14:30 came back as a clash with alternatives on the *following* evening, twice, because a birthday had taken every hour there was to offer. `nonBlockingReason` excuses four kinds: all-day, `transparency: 'transparent'` (Google's "Free" toggle, how a standing working-hours block is normally kept), `eventType: 'workingLocation'`, and an invitation the user declined — the last on the reasoning that put `isDeclined` in front of the briefing. It filters the `busy` list in `suggestAlternativeSlots` too, or the two contradict each other and a day has no conflict and still no free slot. What is excused rides back as `alsoDuring` rather than being dropped: the point is to stop vetoing, not to stop noticing. And a check the protected person cannot overrule is a lock — the failure result now names `ignoreConflicts=true` and the system prompt says a clash is a question asked once, since two explicit confirmations were ignored while nothing anywhere said what the flag was for. Separately the search for the event to move is ±72h, not ±24h: it is by definition not where it is wanted, and "no, today" about something on Tuesday found nothing and wrote a second copy. Not a week — a weekly series puts one instance inside three days and two inside seven, and a second candidate makes the move refuse outright.

**An hour belongs to whoever's day it is.** Three places asked `Date.getHours()` — the server's clock, UTC on Vercel — for a number that only means something in the user's zone. The night guard in `suggestAlternativeSlots` turned "nothing before 07:00, nothing after 22:00" into 10:00–01:00 for a Kyiv user; it now measures in the offset of the requested time (`isSlotWithinHours`, exported because that bug is visible or invisible depending on where the suite runs). The two callers know that offset differently, which is why fixing one was not enough: `scheduleEvent` arrives with a real offset — its schema rejects `Z` and `+00:00` so that it does — while `optimizeSchedule` works in `Date`s and can only pass `.toISOString()`, always parsed back as `+00:00`, so the guard reverted to UTC for the one caller whose job is rearranging a working day. It passes `timeZone`, which wins. Its own `withinWorkingHours` had the identical bug, enforcing `workDayStartHour`/`workDayEndHour` three hours behind its user; it asks ICU for the zone's wall clock rather than doing offset arithmetic, so DST days come out right too.

**A calendar is chosen from the account, not typed.** Following one used to mean entering its id, which made a calendar reachable only if the user already knew its address — so the two most useful on any personal account were effectively unreachable, Birthdays living at `addressbook#contacts@group.v.calendar.google.com`. It also took the id on trust, and `fetchEventsBetween` drops calendars it cannot read via `Promise.allSettled`: a typo was stored, produced nothing forever, and said so nowhere. `listCalendars()` asks Google what the account has and the settings panel is a list of switches; `getCalendar()` verifies the one case the list cannot cover — a shared calendar the user was sent but never subscribed to — and the stored `summary` is Google's own (`summaryOverride` first, since a rename in Google is the user's) rather than a label typed once and left to drift. `listCalendars` throws rather than returning `[]`, because to a picker "Google would not answer" and "you have no calendars" look identical and mean opposite things. `users.followed_calendars` keeps its `{calendarId, summary}` shape, so none of this needed a migration. The account's own calendar is never stored: Google answers for it both as `primary` and under the user's email, so following yourself by address had it fetched twice on every read — `calendarIdsFor` (`lib/utils/calendars.ts`, dependency-free so the client panel can import the types) drops it by matching the email, since the callers that need this run on cron paths with no session to spend a lookup on.
