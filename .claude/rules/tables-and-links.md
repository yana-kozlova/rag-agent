# Tables, search results and links in replies

**A table could be written and never read, and retrieval was standing in for the reader.** Every other table tool writes; `listTables` reports a row *count* and no rows; so the only route to a table's contents was `getInformation`, which is a top-k semantic search behind a hard `MAX_RESULTS = 5`. Asked "скільки разів Арчі прийняв апоквель" over a table holding twenty-two such rows, the assistant answered **five** — the number was the size of the cap. Asked to show the table, it recited whatever the search matched, under the column names of a *different* table it had seen earlier in the conversation. Asked again a minute later, it reported that a table of twenty-three rows had no records in it, because that time the search matched nothing. None of the three is a retrieval bug: top-k is what retrieval is for. The bug was that nothing else could answer, so `getTableRows` (`lib/ai/tools/tables/get-table-rows.ts`) does — an exact `total` computed by `count(*)`, the rows themselves keyed by column *name* rather than id, a `contains` filter as a substring over the stored JSON (the model asking for "апоквель" does not know which column holds it), and an explicit `hasMore` so a page boundary can never be read as the end of the table. `buildMessage` states in words which of the two is on the table, on the rule the briefing already follows for weekdays and lateness: anything to be concluded from a number is the application's job, because a model handed `total: 300` beside fifty rows will eventually say fifty. It deliberately does not write — not a correction, not a deletion, on the precedent that closes a task from chat and deletes it from a route.

**A search result is a sample, and it has to say so in the envelope.** `getInformation` returned a bare array. Five results and no statement of what five *was*: a model cannot tell "five matched" from "five is all you get", and there was nothing in the payload to tell it. So the answer is now `{results, returned, capped, message}`, and the message says the thing out loud — a sample of what is stored, never the complete set, never countable, never a table's contents, and here is the tool that reads the whole thing instead. The empty case is separated from the failed one for the reason `fetchEventsBetween` was: `[]` meaning both "nothing matched" and "the search did not run" is how an embedding timeout becomes "у тебе нічого не збережено". An empty result now says explicitly that it is a search result and not a census, since the assistant declaring a table empty on a failed *search* is exactly what happened. The cache still holds the results rather than the envelope — what they are is a property of the results and cheaper to restate than to store — and `KnowledgeResults` reads both shapes so a turn already on screen does not re-render as "nothing found".

**A citation is an address the application supplied, never one the model composed.** Asked where the details of a birthday were kept, the assistant answered with `https://your-link-to-the-resource/` — a link that reads exactly like the saved thing and opens onto nothing, which is strictly worse than naming the note. The prompt rule was already there and could not be followed: `getTimeline` selects whole rows, `resourceId` among them, and mapped it away, so the model was describing a note it had no address for. A date is stored twice — the row keeps the day, the note keeps the wording — so "деталі" is always the note, and `getTimeline` now hands back `/resources/<id>` per event, exactly as `TimelineAxis` links it on the page; a date the user typed straight onto the axis returns null rather than a plausible-looking guess. `analyzeFile` had the same gap with `resource.id` one line above its return, and `getWellbeing` reported on saved data with no address at all. The rule itself moved out of the Knowledge base section, where it read as a fact about `getInformation` results, into the critical rules where it covers every tool that returns a `url` — and it now names the failure it has to prevent: never an absolute `https://…` for anything saved here, never an id dressed as an anchor, never a stand-in. A result without a url is named, not linked.

**And a rule the model has to remember is enforced where it cannot forget.** After that fix the assistant went on writing `[Деталі тут](https://your-link-to-the-resource/)` beside an `addResource` result carrying the note's real `/resources/<id>`, and `[тут](https://your-link-to-the-table/)` about a table — that one half earned, since no table tool returned an address the prompt names (`getTableRows` had one under `tableUrl`, the rest none). Every table tool now hands back `url`, and `groundLinks` (`lib/ai/grounded-links.ts`) checks the reply itself: a target stays linked only when it occurs in what the user said or what a tool returned, and otherwise the link is reduced to its words. The grounds are user and tool messages and never assistant text, because the assistant's own saved replies are exactly where the stand-ins live and counting them would let each one vouch for the next. The app's top-level pages pass unconditionally; an absolute URL whose path is a supplied address loses its invented host; a bare URL nobody supplied is removed rather than unlinked, since as text both surfaces would link it again. It is strict about outside addresses too — a URL the model knows from training keeps its label and loses its link — because the alternative is judging which invented addresses look invented, and `drive.google.com/file/d/…` looks exactly as real as a real one. The web path runs it as `streamText`'s `experimental_transform`, which sits before both the UI stream and `onFinish`, so what the user watches arrive and what the client saves to history are the same text; `settledLength` holds back a link until it is whole (`[Рост` · `ік](/resources/ab` · `c123)`), and the word still being written, which may be the front of a URL. Telegram awaits a finished answer, so `runAgent` grounds `result.text` against `response.messages`. The five replies saved before this are not rewritten: `isReachableUrl` (`lib/utils/links.ts`) refuses a host with no dot or one of the RFC 2606/6761 reserved names, so the renderer shows them as plain words, and `loadRecentTurns` strips them before replaying history — a stand-in in the assistant's own earlier words is an example to follow.

**Copying rows between two tables is the operation that had no tool, so it was improvised out of a search.** Asked to move the dog's medication rows from one table to another, the assistant had `extractToTable` (which reads *notes*) and `getInformation` (which reads five of anything), so it retyped what the search returned — and the search, asked about "прийом ліків", returned the user's own wellbeing check-in: *"[2026-08-09] 20:48 · головний біль випила хелпекс"*. Their headache pill was written into the dog's table as a row that had never existed. Five rounds of correction followed, each appending more nearly-right rows and each reported as "готово, тепер коректно". With a reader in place the operation is `getTableRows` → `addTableRows` and the prompt says so; what remains is that `addTableRows` only ever appends, which the tool description and the prompt now both state, because a correction written as another row leaves both. `findDuplicates` runs *before* the insert, so it can only match a row that was already there, and reports rather than refuses — the tasks index refuses, but it has an identity narrow enough to be sure, and here two identical rows can be genuinely meant (two coffees, a table with no date column). Swallowing the second silently is unrecoverable; a visible duplicate is one click from gone. What it ends is the silence: the write it cannot prevent, it can at least refuse to call a clean save.

**A row can hold a file, and the file is a resource.** The column types were `text, number, date, boolean, email, url` — so a table about documents could name a document and never hold one, which is why a "Medical Tests" table existed with a column describing PDFs it had no way to keep. A `file` cell stores `{resourceId, name}` and the upload goes through `/api/resources/upload`, the same door as every other file: it is extracted by `unpdf`/`mammoth`, or described by the vision model when it is a photo, then chunked and embedded, so an attachment is searchable by `getInformation` the moment it lands and there is still exactly one path that puts bytes into storage. A blob URL in the cell would have been half the work and a file nothing can find — the mistake "images are stored as text" exists to prevent. The name rides beside the id rather than being looked up, so the table renders without a join, `convertRowToText` embeds "аналіз крові.pdf" instead of an id nobody will search for, and a resource later deleted leaves a cell that still says what was attached. Detaching does not delete the resource: it was read and embedded, and a row no longer pointing at it is not a reason to destroy it. `coerceValue` admits only an actual attachment, which is what makes the type safe to expose to `createTable` — the model can create a file column, cannot forge a value for one, and `addTableRows` says so rather than reporting an upload it did not do. `detectRepeatingRow` skips file columns outright: a button writes without asking and a Telegram reply is text, so the best an attachment could do in a routine is repeat one scan on every press. And `create-table.ts` had kept a private copy of the type list — the exact drift `lib/utils/table-columns.ts` was created to end, reappearing the moment a type was added — so it now imports the one list, as the new-table form's options do.

**A card answers "is this the one, and is it still in use".** The tables list showed three things and two of them were wrong. "4 columns" says how wide a table is and never what it holds; "View rows" was a `<span>` styled like a link and wired to nothing; and "Updated: August 27, 2026 at 10:06 AM" was `userTables.updatedAt`, which only `updateUserTable` touches — so a table written to every morning went on advertising the day its columns were last edited, the one date that cannot say whether it is still alive. The card now carries the row count, when the last row was written, and the column names, which are what "4 columns" was standing in for. Both numbers come from one grouped query (`tableRowStats`) rather than a correlated subquery per table, and that is correctness rather than taste: written as `(SELECT COUNT(*) … WHERE user_table_id = ${userTables.id})` inside a `sql` template, drizzle renders the outer reference **unqualified** on a single-table select, so Postgres read `WHERE user_table_id = "id"` and bound that bare `id` to `user_tables_data` itself. Every table counted the rows whose foreign key equalled their own primary key — zero, always, with no error and no empty result to notice, while the same expression in the `ORDER BY` of the same statement came out fully qualified. The page announced "No rows yet" over a table filled that morning, and `listTables` had been telling the model that every table on the account was empty, which is the exact claim `getTableRows` exists to stop it making. Aggregating from column objects removes the class of mistake: the grouping column is a column, not a string a template has to qualify correctly. The list is ordered by the later of the two dates (`byActivity`, in the application, since the rows are already in hand) so daily use outranks an old rename while a table created moments ago and still empty stays on top, an empty table says "No rows yet" rather than nothing, and the delete confirmation names the number of rows about to go. `relativeTime` moved to `lib/utils/relative-time.ts`, where the dashboard's copy of it now also lives.
