# Google access and refresh tokens

**A refresh token is not forever, and every surface used to report the symptom instead of the cause.** Google ends one when the user revokes access, when they change their password, and — the case that actually bites — after **seven days** for any OAuth client still in "Testing" publishing status. So a deployment works perfectly and loses its calendar a week later, while the session goes on being valid for weeks: signing in is not the same as having Google access, and "увійдіть у застосунок ще раз" was advice that could not be followed, because a live session makes `/signin` bounce straight to the dashboard. What the user saw was a briefing saying the calendar could not be read, a bot saying "щось пішло не так на моєму боці", and nowhere at all the words "grant access again". `lib/auth/google-access.ts` is the shared vocabulary that fixes it: `classifyGoogleTokenFailure` reads a failed refresh as either `expired` (Google's `invalid_grant` — the permission is gone) or `unavailable` (a timeout, a 5xx, or an `invalid_client` that means *this deployment's* credentials are wrong), and only `needsReconnect` cases are ever put to the user. That is the `images:prune` rule again — only an explicit refusal counts as gone — and it is load-bearing in a new way here: a message that means "act now" is spent every time it goes out over an outage the user cannot affect, and after two of those it is not read at all. Both token modules classify through it (`lib/auth/google-token.ts` for web and Telegram, `lib/push/google-token.ts` for cron, whose `getAccessTokenResult` exists so the briefing learns the reason without a second round-trip).

The repair is one flow with three doors. `/google` in the bot checks live and answers one of three ways — alive, ended (with the numbered steps and the link), or Google not answering (wait, and here is the link anyway) — and it is a command rather than something the agent handles, on the `/unlink` precedent: it is asked exactly when the assistant is half-broken, so an answer that depends on the model working is an answer that may not come. Settings → Google (`app/settings/GoogleAccessPanel.tsx`, `GET /api/google/status`) holds the button itself, which calls `signIn('google')` outright rather than linking to `/signin` — the provider already sets `prompt: 'consent'`, so this always returns a fresh refresh token, which `persistGoogleAccount` writes to the account row that cron and Telegram read. And the morning briefing carries the news, because it arrives whether or not anyone opens the app, which is precisely how a dead permission went unnoticed for five days: `CalendarProblem` splits the `events === null` case in two, so `copy.briefing.googleAccessExpired` names `/google` and the plain `calendarUnreadable` no longer guesses at a cause it cannot see. The status is always checked by minting a token rather than by reading `accounts.expires_at`, since that column is only as fresh as the last background job and a status panel that can be confidently wrong is worse than none.

Two supporting fixes were needed, both of them the same bug one layer down. `getCalendarUserOrThrow` throws a typed `GoogleAccessError` whose message is written *for the model* — the AI SDK feeds a failed tool call back into the conversation, so that text is what the assistant reads before answering, and it says in as many words never to report an empty day. And `refreshAccessToken` in `app/api/auth/auth.ts` now drops the access token on failure instead of spreading `...token` over it: keeping it meant every web caller saw "there is a token", handed Google an expired one, and got back a 401 that surfaced as "could not read your calendar" — the one phrasing that hides the only actionable fact. Nothing is lost by dropping it, since that branch is only reached once the token has expired anyway.
